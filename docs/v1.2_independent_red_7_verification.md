### 3.1 R1 工程定义复用层缺失

- **第三方主张**：工程定义复用关系未建模——多个构件/生产计划无法稳定引用同一份 drawing revision / BOM revision / route template / route template step。
- **核验方法**：不机械找"reuse"实体，逐项检查四类工程定义能否被多对象共享引用。
- **当前模型证据（Domain Model）**：
  - 图纸：关系 59 `drawing → drawing_revision 1—N（必须，至少一版）`；关系 60/61 `drawing_revision → engineering_binding → component_list_item / actual_component`，**绑定到清单行时其全部实际构件继承，允许单件覆盖**——一份图纸版次被多构件共享引用，结构存在。
  - BOM：`component_bom_template` 挂 component_list_item、**随图号版次版次化**（3.4）；同清单行的全部实际构件实例化时共享同一模板（part_instance 溯源到 bom_template_line）。
  - 工艺路线：关系 39 `route_template → route_template_step 1—N（必须）；route_template 可指 main_project 和/或可空 subproject（N-6）`——模板挂主项目级即天然被多子项目/多构件共享；step 被计划行（38）与任务（41）引用。
- **业务规则证据**：P-22 要求导入清单时把图号/版次/图元标识作为构件清单字段落库（防二期点模型回头清洗）；C-9 路线匹配维度五级优先级。
- **整改证据**：**MCR-1（R09 工程定义历史快照/版本锚定）正是"route_template 模板行不可变 vs 版本化"的待裁决项**——即"引用是否稳定"这半个问题已在 MCR 清单中，等 ChatGPT 裁决。
- **最终判断**：**PARTIALLY_CONFIRMED**。"复用层缺失"的主张不成立——四类工程定义均可经**共享版本化实体 + 绑定关系**复用，复用本身**不需要独立实体**；但"多个构件能否**稳定**引用同一份定义"依赖模板行版本锚定方式，该点未决——而它恰是 **MCR-1 的裁决点**，非新增问题。
- **是否 NEW_MODEL_GAP**：否（有效内核与 MCR-1 重复）。
- **是否与 MCR 重复**：**是——MCR-1（R09）**。

### 3.2 R2 route_template → actual_component 绑定路径未定义

- **第三方主张**：`actual_component → production_plan → production_plan_line → route_template_step → production_task` 无法反向确定具体 route_template，即"一个构件为什么走这套路线"无法回答。
- **当前模型证据**：
  - 关系 38：`production_plan_line → actual_component N—1（必须）；→ route_template_step N—1（必须）`，**最低粒度=构件+工序步骤实例**（RED-10 连带：同一 operation_type 出现两次为两个不同计划行）。
  - 关系 39：`route_template → route_template_step 1—N（必须）`——step 必属一个 template，**反向可达完整 route_template**。
  - 关系 41：`production_task → route_template_step N—1（必须，工序步骤实例=任务身份的工序维度，R2-06）`——即使脱离计划（补件/计划外），任务自身也必须锚定 step。
  - 唯一性（第 5 章）：production_plan_line=(plan_version_id, actual_component_id, route_template_step_id)；production_task=(actual_component_id, route_template_step_id, attempt)。
  - **结论：从任一 actual_component 出发，经计划行或任务必达 route_template_step，再经关系 39 必达 route_template。绑定路径在模型中已定义且强制（两级"必须"）。**
- **业务规则证据**："为什么走这套路线"由 C-9 匹配规则回答：①子项目+构件类型 → ②子项目默认 → ③主项目+类型 → ④主项目默认 → ⑤全局类型，V1 先用主项目级模板+主管批量调整；N-6（是否需要子项目级模板）为已登记待决项。
- **最终判断**：**NOT_CONFIRMED**。路径已定义、可反向确定 route_template；"为什么"属匹配规则（C-9 已有，N-6 待决是业务选项不是结构缺口）。
- **是否 NEW_MODEL_GAP**：否。**是否与 MCR 重复**：否。

### 3.3 R3 生产状态机与物流位混淆

- **第三方主张**：生产状态与质量/包装/发运状态混在同一状态机（测试链：生产完成→待检→合格→待包装→已包装→待装柜→已装柜→已发运）。
- **当前模型证据（第 10 章，逐机分列）**：
  - 10.2 **实际构件状态机——生产状态与质量状态"分开两套"**：生产状态 `not_started→in_production→(paused)→production_completed→(后续位置态) in_stock→on_pallet→in_container→shipped→site_received`；质量状态**独立** `pending_inspection→first_pass/failed→reworking→reinspection→final_qualified`；明文 **"生产完成不写质量状态；质量结论不回改报工事实"**。
  - 10.3 任务状态机独立（暂停/取消写 task_event，**不修改任何计划行**）；10.4 质量检验单状态机独立；**10.7 托盘状态机独立**（`empty→in_use→loaded→in_container→empty`，repack 是事件不是状态，全程 pallet_load_history）；**集装箱状态机独立**（`empty→loading→sealed→shipped→returned/emptied→empty`，写 container_load_history）；**10.8 发运状态机独立**（`draft→confirmed(快照冻结)→in_transit→delivered`，退运/补发走新 shipment）。
  - 测试链逐段归位：生产完成=任务/报工维度；待检/合格=质量维度（10.2 质量套+10.4）；待包装/已包装=成品入库+托盘维度（finished_goods_stock 一件一行+10.7）；待装柜/已装柜=集装箱维度（10.7）；已发运=发运维度（10.8）——**各为不同业务维度、不同状态机、不同事实源**。
- **需要诚实记录的一点**：10.2 生产状态链中 `in_stock/on_pallet/in_container/shipped/site_received` 被标注为"**后续位置态**"——构件生命状态变量确实**跨越了生产与物流位置语义**。但这不是"混用同一状态机"：托盘/集装箱/发运各自的**操作状态机独立存在**，构件生命状态是由任务/报工/装载等**事实聚合推导的当前值**（"由事实聚合建议，关键节点系统自动迁移"），位置真值在装载/发运事实与各自状态机中。放行硬校验由 releasable/shippable 推导态承担（RED-09）。
- **业务规则证据**：P-23——点开构件的实时状态（当前工序/质量/库存位置/托盘/集装箱/发货状态）由服务层按各事实源实时聚合，页面"状态"是聚合展示，不是同一状态机。
- **整改证据**：约束 6"生产事实与检验事实分表，构件生产状态/质量状态两个独立状态位，状态机分别迁移、互不写对方"；风险检查 #11（生产完成/质量合格混淆 ✅ 双状态机+驾驶舱双率两套事实源）、#17（托盘/集装箱历史 ✅）、#18（发运快照 ✅）。
- **最终判断**：**NOT_CONFIRMED**。九套状态机分列、生产/质量明文隔离、物流三对象各自独立成机；构件生命状态含位置态是有意的事实推导聚合（并已被风险检查收口），不构成"生产状态机与物流位混淆"的结构缺陷。
- **是否 NEW_MODEL_GAP**：否。**是否与 MCR 重复**：否。

### 3.4 R4 plan/task/report 三真相边界未锁死

- **第三方主张**：计划/任务/报工三者真相边界未锁死，可能互相回写。
- **冻结语义核对**：
  - **plan = 计划**：production_plan → production_plan_version（关系 36，**首版即 v1，调整即新版本，旧版不删**）→ production_plan_line（37）；计划变化只能走 plan_adjustment 新版本，**任务暂停/取消不修改任何计划行**（10.3 明文）。
  - **task = 执行任务**：production_task 身份=(actual_component_id, route_template_step_id, attempt)（RED-08/10）；status 只是任务生命周期事实的聚合当前值。
  - **report = 实际执行记录**：RED-07 最终规则——`production_report` 唯一语义=**单次作业事实**（one work-event），不是增量申报/最终申报/状态声明，三类语义禁止混用；**完成数量唯一事实源=有效到件报工行（COUNT）；完成状态唯一事实源=任务生命周期事件；task.status 不得与 report 同时作为独立"完成数量"来源**。
- **业务规则证据**：P-18 双口径（生产完成≠质量合格完成，返工件不计合格完成）；P-23——**计划完成时间=计划行最新版本，实际完成时间=报工事实**，两者分列不覆盖。
- **最终判断**：**NOT_CONFIRMED**。三者边界已被模型结构（版本化计划+身份键）与 RED-07/08/10 整改决议双重锁死，production fact 的唯一真相=有效报工事实行（数量）/任务生命周期事件（状态），**不存在也不需要再创建一个"生命周期真相"实体**。
- **是否 NEW_MODEL_GAP**：否。**是否与 MCR 重复**：否（与既有 RED-07/RED-08/RED-10 收口重叠，属已解决问题）。

### 3.5 R5 part_instance 分类与职责冲突

- **第三方主张**：part_instance 的分类标注与其承担的"当前状态"职责冲突。
- **分类图例（73 行，先立标准）**：**A=当前状态；B=历史事实（只追加）；C=配置/字典；D=业务事件**；B/D 追加后不可静默修改（更正走第 16 域）。
- **part_instance 实况**：
  - **物理实例身份**：是——身份=(actual_component_id, bom_template_line_id, instance_sequence)（422 行），同构件同 part_no 允许多实例；全局代理键。
  - **分类**：标 **B（随件生成、不可静默改）**（102 行）。
  - **current status**：状态机 `planned→material_assigned→cut→consumed_assembled`（旁路 scrapped/substituted/cancelled）。
  - **状态变化历史是否另有记录**：是——迁移全部由**事实触发**（57 行：planned→material_assigned 由套料/领用事实；→cut 由切割结果行；→consumed_assembled 由装配/工序完成事实，**服务层推导**；scrapped/substituted/cancelled 由对应审批事实）；替代 lineage 由关系 87（replacement_of 自引用）+约束 22（指向实例必须 ∈{scrapped,cancelled}）承载，消耗去向由 material_consumption 唯一有效关联（约束 16）承载。
- **判定分析**：part_instance 的状态是**由事实推导的当前值**（与 stock_balance 由 stock_ledger 重建同构），不是独立于事实的第二个真相；实体本身随件生成、只能经事实/更正流程变化，与"B=不可静默修改"不矛盾——**分类标注（B）与状态职责（推导态）在模型文本中已自洽**。冲突仅在"若详细设计把 status 落为可随意改写的物理列"时才会发生，而 57 行已把迁移权收归事实触发。
- **最终判断**：**NOT_CONFIRMED**。不因"有状态字段"判结构错误——状态是事实推导态、历史由事实+lineage 承载、身份/约束齐备，未违反 A/B/C/D 数据分类原则。
- **是否 NEW_MODEL_GAP**：否。**是否与 MCR 重复**：否（lineage 部分与已收口的 R2-02/R2-03 重叠）。

### 3.6 R6 heat_no / internal_batch_no / certificate 追溯锚点未定（高风险项）

- **第三方主张**：Heat/厂内批次/质保书的追溯锚点未定义，链路 `material → material_batch → heat_no → certificate/MTR → material_consumption → actual_component` 可能不闭环。
- **逐锚点核验**：
  - **heat_no 是字段还是独立身份**：heat_no/batch_no 是 **material_batch 身份的组成字段**——批次唯一键=(supplier_id, heat_no/batch_no)（423 行，"炉批号可能跨供应商重复，故组合"）。追溯锚=**批次实体**（携炉批号），Heat 无需独立成实体即被批次身份稳定承载；一次到货可拆多炉批=多批次行（关系 17）。
