## 1. NB-1：生命周期分类主清单

- **修改前问题**：第 18 章仅列部分业务表（T1 42 表/T2 25 表/T3 17 表），约 24 表（imp 域 5 表、eng 域 10 表、material_batch/certificate、purchase_order_item、qr_code_registry、nesting_detail 等）未列入权威清单，Phase 3 建权（revoke UPDATE/DELETE）无逐表依据。
- **最终设计**：第 18 章重建为 **131 表逐张归类权威清单**（18.1~18.8 按 schema 分节）：
  - **A｜正常可更新主数据/当前状态表 = 57**；**B｜Append-only 业务事实表 = 48**；**C｜配置/字典表 = 14**；**D｜事件/审计/导入历史表 = 12**；合计 **131/131 无遗漏**。
  - 每表六项判定：①允许 UPDATE 字段；②事实后不可 UPDATE 字段；③状态推进；④推进须追加事件；⑤void/停用限定；⑥全库统一"严禁物理 DELETE"。
  - 18.9 immutable 字段清单扩充至 16 组（新增 production_report/action_key、material_batch 入口列等）。
- **是否需要 Phase 3 Trigger**：否——本项是建权依据（B/C/D 类回收 UPDATE/DELETE 权限）。
- **是否需要应用层约束**：否。
- **是否影响 Domain Model**：**否**——全部为既有 per-table Lifecycle 声明的清单化归拢；此前未声明表（purchase_order_item、material_certificate、qr_code_registry 等）按其设计语义归类，无结构变更。
- **是否影响业务规则**：否。

## 2. NB-2：append-only 与可更新字段冲突（逐表业务语义决策，未统一选 A/B）

- **修改前问题**：quality_inspection.conclusion、material_consumption.is_effective 在 T1 append-only 表内存在 UPDATE 路径；抽查另发现 material_issue_line.issued_qty（聚合重建列）同类张力。
- **最终设计（按业务语义逐表决策）**：
  - **quality_inspection.conclusion（方案 B——历史结论永久保留）**：`conclusion` 为**一次置值列**（NULL→值仅允许一次，T-9 触发器禁改值/禁清空）。质检结论修正 = **attempt+1 复检新行替代**（`(actual_component_id, inspection_type_id, attempt)` 唯一天然容纳），新旧结论的替代/纠正关系经更正域留痕（correction_request.source_ref → reversal_record.original_ref/redo_ref）。原行结论/缺陷/检验员全部原样保留。
  - **material_consumption.is_effective（不允许手工直接改 FALSE）**：录错消耗的合法路径 = **更正域审批 → reversal_record 新事实行落库 + 反向 stock_ledger 行，同一事务内由 T-10 触发器白名单将原消耗行 is_effective 置 false**；消耗行其余列永远 append-only；冲正行永久保留；重做=新消耗行。`(part_instance_id) WHERE is_effective` 部分唯一索引在全流程中始终有效。
  - **material_issue_line.issued_qty（方案 A 收窄）**：该列为流水聚合的**可重建缓存列**，允许窄路径 UPDATE（T-11：仅过账/对账事务内随聚合刷新，白名单仅此一列）——该表其余列严格 append-only。
  - **component_list_item（NB-8 联动）**：row_status 单向 active→voided（T-12），voided 后语义列禁改。
- **是否需要 Phase 3 Trigger**：**是**——T-9（conclusion 一次置值）、T-10（is_effective 仅冲正事务上下文可置 false）、T-11（issued_qty 白名单）、T-12（voided 冻结），全部**必须数据库强制**（防绕过接口直写历史）。
- **是否需要应用层约束**：是——冲正/更正流程编排（审批→新事实→白名单翻转同事务）、复检替代关系建立。
- **是否影响 Domain Model**：**否**——is_effective/conclusion 字段与冲正域实体均为模型既有项，本轮仅定义其受控更新路径。
- **是否影响业务规则**：是（正向）——明确了"录错消耗/改判质检"的处理方式，补齐了原设计未闭合的执行语义。

## 3. NB-3：report_seq 生成规则（幂等身份与显示序号分离）

- **修改前问题**：report_seq 兼任显示序号与唯一键；换 token 重试（A 超时→B 重发）可能产生两个有效报工。
- **最终设计**（8.4 三层分离表）：
  - `client_token`（部分唯一）= 网络层幂等（同请求重发）；
  - **新增 `action_key VARCHAR(64)`，`(task_id, action_key)` UNIQUE = 业务动作幂等**——客户端按扫码动作生成稳定标识（terminal_id+本地动作序号），**换 token 重试动作键不变**，唯一键拦截 ⇒ 服务端按动作键反查首次行原样返回；
  - `report_seq` = 服务端报工事务内 `max+1` 发放的显示序号，**无唯一约束、不承担幂等职责**，永不重号（同 task 内）。
- **是否需要 Phase 3 Trigger**：否（唯一索引承载）。
- **是否需要应用层约束**：是——客户端动作键生成规则（动作不重复提交则本地序号不重置）。
- **是否影响 Domain Model**：**否**（新增物理字段，模型关系/不变量零变更）。
- **是否影响业务规则**：是——明确"同一实际生产动作至多一行有效报工"的物理保证方式。

## 4. NB-4：Trigger 类约束设计（13.1 设计清单，本轮不写 SQL）

- **修改前问题**：约束 8/22/24/28/33/import_row 依赖触发器但无设计定义。
- **最终设计**：13.1 表 T-1~T-12，每项含：Trigger 目的 / BEFORE / UPDATE·DELETE 事件 / 阻止什么 / 事务边界 / **强制层归属**。
  - **必须 DB 强制**（核心历史不可变）：T-1 快照冻结(约束8)、T-4/T-5 模板行禁改(24)、T-6 make_type 终局(28)、T-7 material_code 禁改(33)、T-8 import_row 处理后冻结(29)、T-9/T-10/T-11/T-12（NB-2/NB-8 白名单）。
  - **应用层主校验 + DB 兜底**：T-2/T-3 替代指向态(22)。
  - **应用层为主、不建触发器**：约束 9/10/18/25/31。
- **是否需要 Phase 3 Trigger**：**是（12 项，Phase 3 Migration 实现）**；**不得再出现"Phase 3 再看"**——设计已定案。
- **是否影响 Domain Model**：否。**是否影响业务规则**：否。

## 5. NB-5：期初/手工批次入口

- **修改前问题**：约束 32"批次生成唯一入口=receipt_item 验收"与关系 17 可空 receipt_item_id（期初/手工批次）存在语义张力，例外入口无审批/审计要求。
- **最终设计**（6.1）：`material_batch` 新增 **`batch_source CHECK ∈ {receipt_acceptance, opening, manual}`**（默认 receipt_acceptance）；**CHECK：batch_source='receipt_acceptance' ⇒ receipt_item_id NOT NULL；'opening'/'manual' ⇒ 必空且 source_ref/approved_by/approved_at 非空**；审批事实另经 aud.approval_record + 全部创建动作写 operation_log。约束 32 修订为"**默认唯一入口=验收事务；例外仅 batch_source∈{opening,manual} 且强制审批留痕**"。
- **是否需要 Phase 3 Trigger**：否（CHECK+唯一入口结构承载）。**是否需要应用层约束**：是（例外入口审批流程与期初迁移脚本走该入口）。
- **是否影响 Domain Model**：**否**——关系 17 仍为 Optional FK，约束 32 业务语义不变，属字段级实现细化。
- **是否影响业务规则**：是——明确例外入口必须有来源+审批+审计，不放开任意创建。

## 6. NB-6：site_delivery_record.component_ref 定案

- **修改前问题**：component_ref 列形态未定义（非 FK、非标准软引用对）。
- **最终设计**（11.6）：**`actual_component_id BIGINT NOT NULL FK → prod.actual_component ON DELETE RESTRICT`**——签收目标类型单一（构件），采用强 FK 而非多态软引用；shipment_id 可空 FK 保留；关系 79 由 SOFT(经快照) 升级为 MF+OF 复合（102 总数不变）。
- **是否需要 Phase 3 Trigger**：否。**是否需要应用层约束**：否。
- **是否影响 Domain Model**：**否**（模型该关系本即指向构件；仅物理形态定案）。
- **是否影响业务规则**：否。

## 7. NB-7：stock_balance 索引

- **修改前问题**："库位→现存批次/材料"查询路径缺前导索引（唯一索引前缀为 batch→location，方向不匹配）。
- **最终设计**（7.4/16.2）：新增 **`stock_balance(storage_location_id, material_batch_id)`** 复合索引；扣减事务主路径仍走唯一索引 `(material_batch_id, storage_location_id)` 前缀——两条路径各用其索引，**不盲目加列索引**（不加 weight_kg 等低选择性索引）。
- **是否需要 Phase 3 Trigger**：否。**是否需要应用层约束**：否。**是否影响 Domain Model**：否。**是否影响业务规则**：否。

## 8. NB-8：导入修正版"失效"物理落点

- **修改前问题**：修正版 Excel 中被删除/取消的原始业务记录无受控状态表达；"人工决策失效"无物理语义。
- **最终设计**（5.2/5.3/5.6/19.G）：
  - `import_row.result_status` 值域扩展：created/updated/kept/failed/conflict/rejected/**invalidated**——修正版缺失的 source_identity 落 invalidated 行留证（corrected_from_row_id 指向原行，raw_payload 存差异说明）；
  - `import_correction_result` 新增 **`rows_invalidated`** 计数（decided_by/at 决策留痕）；
  - `component_list_item` 新增 **`row_status ∈ {active, voided}`**——人工批准后置 voided，**voided 行保留全部原值原身份、严禁 DELETE、语义列触发器禁改（T-12）、禁被新引用**；
  - **业务规则四条**：①"Excel 无此行"≠自动删除——失效必须落 invalidated 待人工批准；②仅未实例化（无 actual_component/无 plan_line 引用）的清单行允许经导入修正失效；③已进入生产的对象自动失效被拒绝（result_status='conflict' 走人工/更正域）；④material/批次/库存/生产/质量/发运不在导入失效能力范围内（V1 导入域仅覆盖构件清单）。
- **推演（500→8 改/3 增/2 失效）**：第二批 500 行重放 ⇒ 487 kept + 8 updated + 3 created（同 source_identity 幂等）+ 2 invalidated（原批次对应行不动）⇒ 人工批准 ⇒ 2 个 component_list_item 置 voided ⇒ **原业务记录零物理删除，两批次原文完整留存**。
- **是否需要 Phase 3 Trigger**：**是（T-12 voided 冻结，必须 DB 强制）**。**是否需要应用层约束**：是（invalidated 待处置清单+人工批准流程+已实例化拒绝规则）。
- **是否影响 Domain Model**：**否**——row_status 为既有清单行实体的字段级细化，未新增实体/关系/约束（计数 130/102/34 不变）。
- **是否影响业务规则**：是（正向）——补齐导入修正的受控失效语义，防"Excel 缺行误删生产数据"。
