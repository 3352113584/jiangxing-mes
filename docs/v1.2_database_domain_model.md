## 1. 领域模型总览

### 1.1 核心设计立场

1. **以 actual_component（实际构件）为唯一核心数字实体**。它是生产履历、质量履历、材料追溯、任务/报工、包装、装柜、发运、现场扫码的汇聚点；围绕它建立全部关系。
2. **四类数据严格分表，不建万能表**：
   - A 当前状态（如 actual_component 的当前状态、托盘当前装载状态）；
   - B 历史事实（报工、检验、装载历史、发运快照——只追加、不可覆盖）；
   - C 配置/字典（工序、检验类型、异常原因分类、单位等）；
   - D 业务事件（状态变更、暂停/恢复、更正申请、审批）。
3. **三条不可逾越的分离**：计划 / 任务 / 报工分离；主责班组 / 执行班组 / 实际人员分离；生产完成 / 质量合格分离。
4. **数量语义七类分列**，不存在一个万能 quantity；actual_component **永远隐含数量 1，禁止出现 quantity 字段**。
5. **当前值与历史双轨**：关键业务对象既有"当前状态"又有"只追加历史"；当前值可由系统重建，历史事实不可被 UPDATE 覆盖（更正走申请+冲正）。
6. **结构化优先**：核心业务关系全部用实体与关联表达；JSON 仅允许用于非关系型附注，不得承载核心关系、状态或数量。
7. **业务编号与数据库代理键分离**：内部 id 无业务含义；业务编号单独建模、定义唯一范围。

### 1.2 核心实体（领域主干）

| 中文 | 英文名 | 角色 |
|------|--------|------|
| 主项目 | main_project | 顶层合同/工程单位 |

### 1.3 数据主线（一条主链 + 三条支撑链）

- **主链（构件价值流）**：
  main_project → subproject → component_list_item → actual_component →（bom_template_line →）part_instance → **material_consumption（实际材料消耗，实际材料来源权威事实）** → production_plan_line → production_task → production_report → quality_inspection（→ rework → 新 attempt）→ finished_goods → pallet_load → container_load → shipment_snapshot → 现场。
  （注：nesting_detail 是**计划层**套料事实，用于计划对比，不在实际材料来源主链上——R2-01）
- **材料链（双向追溯必须闭环）**：
  purchase_order → purchase_receipt → weighing_record → material_batch（+material_certificate）→ stock → nesting_batch → cutting/consumption →（part_instance → actual_component）；余料 surplus_material、废料 scrap_record 不断链。
- **责任链**：actual_component → primary_team（当前主责+变更史）；production_task → execute_team（唯一）；production_report → worker（多个实际人员）。
- **计划链**：production_plan（月/周/日）→ plan_version（版本留痕）→ plan_line（构件+工序）→ task → report；计划永远不被报工回写。

## 2. 核心业务主线（分域流转）

1. **项目流**：主项目建档 → 子项目建档（八态生命周期，全程状态史）。
2. **技术数据流**：外部工程对象+图纸+图纸版本导入 → 构件清单（图号/版次/工程对象标识/安装位置）→ 按 quantity 生成实际构件与 QR → BOM 模板实例化为零件实例。
3. **物料流**：需求计算（BOM×清单量）→ 采购（可跨主项目，N-4 预留）→ 到货 → 供应商/厂内双过磅 → 材料批次/炉批/质保书 → 库存（一本流水）→ 套料结果导入 → 切割下料 → 实际消耗 / 余料回池 / 废料。
4. **生产流**：月/周/日计划（版本化）→ 工艺路线生成任务（到件到工序）→ 主责班组指派 → 执行班组派工（允许协作，不改主责）→ 扫码报工（到件到人、幂等）。
5. **质量流**：生产完成 → 待检 → 一次合格 / 不合格（多缺陷、NCR）→ 返工生成新 attempt 任务 → 复检 → 最终合格；检验事实只追加。
6. **包装发运流**：成品入库（一件一行）→ 托盘装入/拆出/重装（留史、超重拦截）→ 集装箱装柜/卸柜/复用（同主项目为界、跨主项目授权例外）→ 发运确认出快照（不可变）→ 运输/现场签收（扩展位）。
7. **治理流**：设备事件影响链、图纸变更影响链、统一异常中心、事实更正/冲正、审批记录、操作审计、站内消息，横切以上各流。

## 4. 实体关系（类型、基数、是否必须）

> 记法：1—1 一对一；1—N 一对多；N—1 多对一；N—M 通过中间实体。**必须**=子实体不可脱离父实体存在。

### 4.1 项目 / 构件主干

1. main_project → subproject：1—N，必须。一个主项目有多个子项目；子项目必属一个主项目。
2. main_project → project_status_history：1—N，必须。主项目状态史。
3. subproject → project_status_history：1—N，必须。子项目状态史（同一状态史实体用"对象层级"区分主/子项目）。
4. subproject → component_list_item：1—N，必须。清单行必属一个子项目。
5. component_list_item → actual_component：1—N，必须。N=清单 quantity；quantity=1 也必须生成 1 个；报废补件也挂同一清单行。
6. subproject → actual_component：1—N，必须（经清单行上溯；构件表直接持 subproject 归属为事实键）。
7. actual_component ↔ qr_code_registry：1—1，必须。全局唯一码，码与件终身绑定（报废也不释放给别人）。
8. actual_component → component_scrap_record：1—N（0..N）。一构件至多一次生效报废；历史可多次申请记录。

### 4.2 BOM / 零件

9. component_list_item → component_bom_template：1—N（按图纸版次，当前生效一个），必须。模板挂清单行。
10. component_bom_template → bom_template_line：1—N，必须。
11. bom_template_line → part_instance：1—N（N=清单 quantity，一件一实例行/件的零件集），必须。
12. actual_component → part_instance：1—N，必须。零件实例必属一个实际构件；模板行与零件实例并存，是"共性 vs 到件追踪"分离（N-10）。

### 4.3 采购 / 材料 / 库存

13. purchase_order → purchase_order_item：1—N，必须。
14. purchase_order_item → po_item_allocation：1—N（可 0：公司级未分摊时；N-4 预留）。分摊行指向 subproject。
15. purchase_order → purchase_receipt：1—N。可分批到货。
16. purchase_receipt → purchase_receipt_item：1—N，必须。
17. purchase_receipt_item → material_batch：1—N（一次到货可拆多炉批/多批次），必须。
18. material_batch → material_certificate：N—1（多批可共用一质保书；一批至少一质保书或允许登记缺失状态，缺失则预警）。
19. material → material_batch：1—N，必须。
20. material_batch → stock_balance：1—N（按库位）。
21. stock_balance → stock_ledger：由流水追加维护（流水是事实源，余额可重建）。
22. material_batch → weighing_record：1—N。一到货/一批可多次过磅。
23. purchase_receipt_item / material_batch → weight_discrepancy：1—0..1/1—N（按业务登记口径）。
24. subproject → material_requirement：1—N，必须。需求单头必属子项目。
25. material_requirement → material_requirement_item：1—N，必须。

### 4.4 套料 / 消耗 / 余废料

26. nesting_import_batch → nesting_batch：1—N。
27. nesting_batch → nesting_detail：1—N，必须。
28. nesting_detail → material_batch（母材）：N—1，必须。明细必有所耗母材批次。
29. nesting_detail → part_instance（计划零件）：1—1 或 1—N，**可选（计划关系，R2-01）**——有正式套料计划时建立，用于计划对比与利用率统计；**允许零件无套料计划直接实际加工**（补件、散件/直发件、小批量：实际来源直接由 material_consumption 记录，不强迫先有套料明细）。此关系不是实际材料来源依据。
29a. material_consumption → part_instance（被产出零件实例）：N—1，**必须（实际事实关系，R2-01）**——每次实际消耗落到具体零件实例；这是实际材料来源主链的强制环节。
29b. material_consumption → 实际来源（material_batch ｜ surplus_material）：N—1，**必须（实际事实关系，R2-01）**——实际炉批/实际材料来源只能由本关系确定；planned_source_ref（→ nesting_detail 或计划批次）为**可选**对比引用，计划≠实际时 substitution_reason 必填，**计划历史不被覆盖**。
30. nesting_batch → cutting_record：1—N（一批可分多次切割）。
31. cutting_record → cutting_result_line：1—N，必须。
32. cutting_result_line → material_consumption：1—1/1—N，必须。消耗事实可经明细关联 part_instance 与批次。
33. material_batch → surplus_material：1—N。余料带来源批次；surplus_material 再被领用时通过新的 material_consumption 指向该余料（余料也视为可耗材料实体，与批次同构或同表多态——详细设计定，领域上要求**来源/去向双向可查**）。
34. material_consumption → scrap_record：1—0..N。

### 4.5 计划 / 任务 / 报工

35. subproject → production_plan（头）：1—N，必须。
36. production_plan → production_plan_version：1—N，必须（首版即 v1，调整即新版本，旧版不删）。
37. production_plan_version → production_plan_line：1—N，必须。
38. production_plan_line → actual_component：N—1，必须；→ route_template_step：N—1，必须。**最低粒度=构件+工序步骤实例**（与任务身份对齐；同一 operation_type 出现两次为两个不同计划行，RED-10 连带）。
39. route_template → route_template_step：1—N，必须；route_template 可指 main_project 和/或可空 subproject（N-6）。
40. actual_component → production_task：1—N，必须（按路线每工序；返工加 attempt）。
41. production_task → actual_component：N—1，必须；→ **route_template_step N—1，必须（工序步骤实例=任务身份的工序维度，R2-06）**；operation_type 经 step → operation_type 间接获得（分类/显示用，不是身份）；→ execute_team **单外键（一个任务一个执行班组）**；→ primary_team 不直接关联（主责挂构件，不挂任务）。
42. production_task → task_participant：1—N（多人）。
43. production_task → task_event：1—N，必须。
44. production_task → production_report：1—N（正常一任务一完工报工，但允许多次部分报工/多人员分批提交——是否允许分段报工由操作配置定，领域允许 1—N）。
45. production_report → production_report_worker：1—N，必须（至少一人）。
46. production_report → production_measure：1—N（重量/长度/工时独立行，不塞 quantity）。
47. actual_component → primary_team_assignment：1—1 当前；1—N 历史（primary_team_change_history）。
48. production_plan_line ↔ production_task：1—N（计划行可对应多个 attempt 任务；首个任务对齐计划，返工任务指向原计划行或标注计划外——详细设计保证统计不重复计数）。

### 4.6 质量 / 返工

49. actual_component → quality_inspection：1—N，必须。
50. quality_inspection → quality_defect：1—N（0 个缺陷即合格）。
51. quality_inspection → ncr：N—1（多检验/缺陷可归一 NCR；NCR 可覆盖多构件）。
52. ncr / quality_inspection → rework_order：1—N。
53. rework_order → production_task（新 attempt）：1—N，必须。返工不改写原检验与原任务。
54. actual_component → final_qualification：1—0..1 当前结论；历史结论只追加（最终合格事实以最新放行事件为准，但历次放行/撤销均可追溯）。

### 4.7 设备

55. equipment → equipment_event：1—N，必须。
56. equipment_event → equipment_impact：1—N。
57. equipment_impact → production_task：N—1，必须；构件/班组/计划经任务→构件→主责/执行班组→计划行得到，不复制事实。

### 4.8 图纸 / 变更

58. engineering_object → engineering_binding：1—N。
59. drawing → drawing_revision：1—N，必须（至少一版）。
60. drawing_revision → engineering_binding：1—N。
61. engineering_binding → component_list_item / actual_component：N—1（绑定到清单行时其全部实际构件继承；允许单件覆盖绑定）。
62. drawing_revision → engineering_change（新版入口）：1—N；engineering_change 同时关联旧版 drawing_revision。
63. engineering_change → engineering_change_item：1—N，必须。
64. engineering_change_item → change_disposition：1—1；change_disposition 可 1—0..1 关联 rework_order。

### 4.9 异常 / 更正 / 审批 / 审计

65. exception_event → exception_impact：1—N，必须（至少描述一个影响范围，聚合级异常可只到计划/子项目）。
66. exception_event → exception_handling：1—N。
67. 任意业务事实 → correction_request：通过"原始对象类型+原始对象 ID"关联（结构化引用对，不是 JSON）；correction_request → correction_approval 1—N；→ correction_entry/reversal_record 1—1/1—N。
68. approval_record 以"审批对象类型+对象 ID"服务于 plan_adjustment、mixed_load_authorization、task_cancellation、correction_request 等，不复制各业务审批状态。
69. operation_log 与所有业务实体：技术级记录关系（日志持对象类型+ID+操作），不作为业务凭据。

### 4.10 成品 / 包装 / 集装箱 / 发运

70. actual_component → finished_goods_stock：1—0..1 当前（一件一行，出库后状态流转但行保留）。
71. actual_component → pallet_load：1—0..1 当前有效装载。
72. pallet → pallet_load_history：1—N，必须；pallet_load 当前关系由历史最新事件维护。
73. pallet → container_load：N—0..1 当前（当前所在箱）。
74. shipping_container → container_load_history：1—N，必须。
75. shipping_container → pallet（当前）：1—N。
76. shipment → shipping_container：1—N（一发运多箱；箱循环复用时历史发运关系不可改——经发运快照保存）。
77. shipment → shipment_snapshot：1—N，必须；shipment_snapshot → actual_component N—1，必须（**逐构件快照行**，并冗余当时托盘/集装箱/重量/子项目）。
78. shipment → shipment_event：1—N，必须。
79. actual_component → site_delivery_record：1—0..N（正常 1 次；退运补发可多次）。

### 4.11 人员 / 权限

80. employee → team_membership：1—N（当前主属一条，历史多条）。
81. employee → secondment_record：1—N。
82. employee ↔ user_account：1—1（系统用户必须有员工档案；纯系统账号除外）。
83. user_account → user_role → role → role_permission → permission（标准 RBAC 链）。
84. role/user_account → data_scope_policy：1—N（五档范围及具体范围值）。
85. employee/team → production_report_worker / execute_team / primary_team：执行与责任事实的引用源。
86. **actual_component → actual_component（replacement_for 自引用）：1—0..1（R2-02 结构落点）**——补件实例指向被替代（报废）实例；基数=一个被替代实例至多被一个补件实例替代；约束：replacement_for 非空 ⇒ 被指向实例状态 ∈ {scrapped, cancelled}；**需求数量恒为清单 quantity，完成统计只计有效实例（21.7 口径不变）**。
87. **part_instance → part_instance（replacement_of 自引用）：1—0..1（R2-03 结构落点）**——零件实例替代：保留原件（状态 substituted）、替代件、替代原因、发生时间、审批引用；基数=一个被替代实例至多被一个新实例替代。
88. **material_consumption 计划/实际双层（R2-03 材料替代落点）**：材料替代不是实例替代 lineage，而是"计划来源（planned_source_ref，可选）vs 实际来源（必须）"的差异事实 + substitution_reason；原计划 nesting_detail 永不覆盖。

## 7. 时间体系（发生时间 ≠ 录入时间）

四类时间语义，禁止用一个 timestamp 混用：

| 时间语义 | 含义 | 典型字段（领域层） | 适用对象 |
|---|---|---|---|
| 计划时间 | 计划上的起止/节点 | planned_start_at / planned_finish_at | 计划行、任务（派工计划） |
| 业务发生时间 | 事实真实发生时刻 | **occurred_at**（可含 start/end） | 报工、检验、切割、过磅、设备事件、装柜、发运、签收、暂停/恢复 |
| 录入时间 | 数据进系统时刻（扫码提交） | **recorded_at** | 所有扫码/人工录入事实 |
| 系统审计时间 | 行创建/最后修改 | created_at / updated_at | 全部实体 |
| 审批时间 | 审批动作时刻 | approved_at | 各类审批/更正/调整/授权 |

要点：
- 典型场景：工人 20:00 完工、21:00 扫码 → occurred_at=20:00、recorded_at=21:00；统计口径默认按 occurred_at（允许管理配置，属技术项），审计按 recorded_at。
- occurred_at 允许填报（受权限与合理范围校验），recorded_at 只取服务器时间。
- 历史事实行**不更新 updated_at 语义**（更正产生新行/冲正行，原行冻结）；A 类当前状态行才有 updated_at。
- 任务/设备停机等有持续时长：occurred_start_at + occurred_end_at，时长可由系统计算（计算值，非事实）。

## 10. 状态机

> 下列为领域允许的迁移、操作角色（角色名仅描述职责，最终由 RBAC 配置映射）、原因/审批/历史要求。所有状态迁移**必须**写一条对应历史/事件行。

### 10.1 项目状态机（主项目/子项目同一套八态）

状态：`draft preparing production paused production_complete shipping completed closed`

| 迁移 | 操作角色 | 原因 | 审批 | 历史 |
|---|---|---|---|---|
| draft → preparing | 项目经理/主管 | 否 | 否 | 必须 |
| preparing → production | 生产主管（系统按事实建议+确认） | 否 | 否 | 必须 |
| production → paused | 生产主管 | **必须** | 否 | 必须 |
| paused → production | 生产主管 | 必须（恢复说明） | 否 | 必须 |
| production → production_complete | 系统建议+主管确认（全部构件最终合格） | 否 | 否 | 必须 |
| production_complete → shipping | 主管/仓库 | 否 | 否 | 必须 |
| shipping → completed | 系统建议+确认（全部构件发运完成） | 否 | 否 | 必须 |
| 非关闭态 → closed | **管理权限** | 必须 | 按配置 | 必须 |
| closed → 前置活跃态（重开） | **管理权限** | **必须（重开原因）** | 按配置 | 必须（记录回到的目标态） |

补充：paused 是可与生产阶段并存的挂起态，进入/退出都留史；子项目独立流转，主项目状态由子项目事实汇总建议。

### 10.2 实际构件状态机（生产状态与质量状态分开两套）

**生产状态**：`not_started → in_production →（paused 挂起，由任务暂停传导/可手动）→ production_completed →（后续位置态）in_stock → on_pallet → in_container → shipped → site_received`；旁路 `scrapped`。

- 生产状态由任务/报工/装载等事实聚合建议，关键节点由系统自动迁移；scrapped 终态：报废申请+批准，序号释放规则=不释放。
- 补件：同清单行新 sequence，状态从 not_started 独立走一遍；**新实例必须携带 replacement_for 指向被替代实例（lineage 自引用）；需求数量恒为清单 quantity，完成统计只计有效实例（RED-11）**。
- **releasable/shippable 为服务层推导态：production_completed ∧ final_qualified ∧ 非 scrapped/冻结；包装/装托/装柜/发运动作必须硬校验（RED-09）**。

**质量状态**（独立于生产）：`pending_inspection → first_pass / failed → reworking → reinspection → final_qualified`。
- first_pass 与 final_qualified 在一次合格时可同一事实达成；failed→返工→新 attempt 检验→直到 final_qualified；报废路径可从 failed 进入（经处置）。
- **生产完成不写质量状态；质量结论不回改报工事实。**

### 10.3 任务状态机

`pending → in_progress → completed`；任意活跃态 → `paused`（班组/执行人发起填原因、主管确认生效/恢复）；活跃态 → `cancelled`（**主管权限**+原因+审批记录）。
- 暂停/恢复/取消全部写 task_event；取消后是否重建任务在取消事实中登记。
- **任务暂停/取消不修改任何计划行**；计划变化只能走 plan_adjustment 新版本。
- 返工：不改老任务状态——老任务保留 completed/其检验 failed；新建 attempt+1 任务从 pending 走起，**携带 rework_of 指向老任务；attempt 绑定 route_template_step（工序实例），同一 operation_type 的多次出现互不干扰（RED-08/10）**。

### 10.4 质量检验状态机（检验单自身流转）

`待检登记 → 检验中 → 结论（一次合格 / 不合格）`；不合格关联 NCR 与返工；复检是**新 inspection 行（attempt+1）**；最终合格以 final_qualification 放行为准。检验行一旦出具结论只允许通过更正流程修正，不允许直接改判覆盖。

### 10.5 设备状态机

`running ↔ stopped`；任意运行态 → `fault`（登记故障事件）→ `under_maintenance` → `running`（恢复事件）。当前状态在 equipment，每段起止在 equipment_event；故障事件登记后通过 equipment_impact 关联受影响任务。

### 10.6 异常状态机

`open → processing → closed`（允许 closed 前多次处理记录）；关闭必填关闭信息；异常**原因分类**（七类）与**受影响班组**是两个字段；异常可由系统自动发现生成（open）或人工登记。
- **一因多果**：一个根因异常（exception_event）通过 exception_impact 挂多条影响对象行（构件/任务/工序/班组/计划行）；**禁止**为每个受影响对象复制独立异常（ORANGE-06）。

### 10.7 托盘 / 集装箱状态机

- 托盘：`empty → in_use（装载中）→ loaded（在册）→（装入集装箱）in_container →（卸出/清空）empty`；repack（重新包装）是事件不是状态，全过程写 pallet_load_history。
- 集装箱：`empty → loading → sealed（已封柜）→ shipped → returned/emptied → empty（复用）`；装柜/卸柜/重装写 container_load_history；跨主项目装载在装载动作发生前必须存在有效 mixed_load_authorization。

### 10.8 发运状态机

`draft → confirmed（发运确认=快照生成）→ in_transit → delivered`；旁路/分支：`returned（退运）`、补发以新 shipment 行承载；confirmed 之后 shipment_snapshot 冻结，任何后续业务变化不得改写快照。

### 10.9 更正申请状态机

`draft/submitted → approving → approved → applied（更正或冲正已生效）/ rejected`；被下游引用时 approved 动作必须生成 reversal_record（原事实标冲正+反向/重做事实关联）。

## 11. 删除与作废策略

| 数据类别 | 策略 | 说明 |
|---|---|---|
| 主数据（物料/供应商/人员/班组/设备/工序字典） | **软删除（停用标记）** | 被引用后不可物理删除；停用不影响历史展示 |
| 项目/子项目 | 禁止物理删除；关闭=只读 | 草稿态是否允许删除：仅无任何下游事实的草稿可由管理权限删除（建议默认也软删，详细设计定） |
| 构件清单行 | 已生成实际构件后禁止删除；未生成前可作废 | 导入错误在生成实例前可更正/作废，留痕 |
| 实际构件 | **禁止物理删除**；走错件/误建走更正流程或报废 | 报废≠删除；序号不重用 |
| BOM 模板 | 版次化，不删旧版 | 当前版可切换；已生产零件实例不回改 |
| 零件实例/套料/消耗/余废料 | **禁止删除，只能更正/冲正** | 追溯链完整性 |
| 采购/到货/过磅/批次/质保书 | 禁止删除；错误走更正 | 磅差处理决定不可直接覆盖原始过磅 |
| 库存流水 | **只追加，禁止删除和直接改** | 余额由流水重建；差错走盘点+更正 |
| 计划 | 当前版可调整（生成新版）；**任何版本不删除** | 审批中的调整单可作废 |
| 任务 | 不可删；可取消（留史） | 派工错误走取消+重派 |
| 报工 | **禁止删除/静默改**；更正申请→审批→更正/冲正 | 已质检/入库/计价/发货引用的必须冲正重做 |
| 检验/缺陷/NCR/返工/最终合格 | **禁止覆盖、禁止删除**；错判走更正+重新检验（新行） | 第一次检验永久保留 |
| 设备事件/影响 | 禁止删除；登记错误走更正 | |
| 图纸/版次/变更 | 旧版**禁止删除**；作废以状态标记 | |
| 异常/处理记录 | 禁止删除；可关闭 | 误报异常走"误报关闭"并留说明 |
| 托盘/集装箱装载历史 | **禁止删除、禁止改写**；装入/移除成对事件 | 当前关系由事件推导 |
| 发运单/快照 | 快照**永久冻结**；发运单差错走退运/补发事件，不改快照 | |
| 审批/更正/操作日志 | 只追加，禁止删除和修改 | |
| 配置/字典 | 可停用不可删（被引用时）；代码值稳定 | 名称可改、编码不改 |
| 通知消息 | 可由接收人删除/归档自己的消息（非业务事实） | 站内通知，不影响业务 |

## 12. 业务规则 → 数据完整性约束映射

> 保证层：**DB**=数据库约束可独立保证；**S**=必须服务层保证（数据库无法表达或表达成本过高）；**DB+S**=双层保证。每条说明原因。

| # | 业务规则 | 保证层 | 落地方式（领域层描述） |
|---|---|---|---|
| 1 | actual_component 数量隐含 1 | **DB** | 结构保证：该实体不存在数量列；件数永远是行数 |
| 2 | 子项目+构件号+序号唯一 | **DB** | 三列业务唯一约束 |
| 3 | QR 全局唯一 | **DB** | qr_code 唯一约束；码与构件 1:1 |
| 4 | 一个任务只能有一个执行班组 | **DB** | production_task 持单个 execute_team 外键，不用子表表达执行班组 |
| 5 | 报工不能覆盖计划 | **DB+S** | DB：计划行与报工是不同实体、报工表不持计划目标字段；S：写计划只能经版本化调整接口，报工接口不开放计划写权限 |
| 6 | 生产完成≠质量合格 | **DB+S** | DB：生产事实与检验事实分表，构件"生产状态/质量状态"两个独立状态位；S：状态机分别迁移、互不写对方 |
| 7 | 原始检验不被返工覆盖 | **DB** | 检验唯一键含 attempt；返工只新增 attempt+1 行；检验行只追加 |
| 8 | 发运快照不可被后续数据改变 | **DB+S** | DB：快照为独立行、值为冗余冻结副本而非活外键回引展示；S：确认后无更新接口（只有查询），库账号层面也可回收 UPDATE 权限 |
| 9 | 不同主项目混装须授权 | **S（+DB 佐证）** | DB：授权实体存在、装载事件可关联授权 ID；S：装载提交时校验主项目一致性或有效授权（含原因/审批），否则拒绝 |
| 10 | 超重硬阻止 | **S** | 重量是动态聚合且称重事实可后补，CHECK 无法表达；S：装载事务内聚合当前重量+称重事实并比对承重上限，超限整体回滚；必要时 DB 触发器做兜底（详细设计评估） |
| 11 | 关键事实不能直接覆盖 | **DB+S** | DB：事实表只追加（无业务更新路径）+冲正实体；S：所有写操作经更正审批流；库权限最小化（业务账号无裸 UPDATE/DELETE） |
| 12 | 扫码关键操作幂等 | **DB+S** | DB：client_token（幂等键）唯一约束；S：终端超时重试用同一 token，服务端识别后返回首次结果不重复落库 |
| 13 | 同子项目同构件号清单唯一 | **DB** | (subproject_id, component_no) 唯一 |
| 14 | 报废序号不复用 | **DB+S** | DB：序号发放记录（已用序号集合含报废）；S：发号逻辑只增不回退 |
| 15 | 一件同时只能在一个托盘 | **DB** | 当前装载行对 actual_component 唯一；历史另表 |
| 16 | 材料消耗到零件唯一有效去向 | **DB** | material_consumption 对 part_instance 的有效关联唯一（防一料多记；R2-01 后 nesting_detail→part_instance 为可选计划关系，不承担此约束） |
| 17 | BOM 模板改版不影响已产零件 | **S（+DB）** | 实例化后 part_instance 独立；S：模板改版只影响未实例化部分（或提示差异），不回写实例 |
| 18 | 缺料排产控制（N-16 未定） | **S + 配置** | 系统配置开关：预警（默认建议）/硬拦截；硬拦截时服务层阻止下达，DB 不做不可逆结构 |
| 19 | 计划行粒度=构件+工序步骤 | **DB** | 计划行必须同时非空引用 actual_component 与 **route_template_step**（R2-06 修正；operation_type 仅经 step 间接获得，用于分类统计） |
| 20 | 异常原因≠受影响班组 | **DB** | 原因分类外键与影响班组外键是 exception_impact 上两个独立字段，无派生关系 |
| 21 | 实际材料来源必须 | **DB**（R2-01） | material_consumption 的实际来源（material_batch｜surplus_material）与被产出 part_instance 必须非空；planned_source_ref 可空；substitution_reason 在计划≠实际时必填 |
| 22 | 替代 lineage 完整性 | **DB**（R2-02/03） | actual_component.replacement_for 非空 ⇒ 指向实例状态 ∈ {scrapped, cancelled}；part_instance.replacement_of 同规则（指向 substituted）；替代原因/时间/审批随事实行记录，不可空缺 |
| 23 | 导入修正防重 | **DB**（R2-04） | (subproject_id, component_no, instance_sequence) 唯一幂等复用实例；import_batch.supersedes_batch_id 非空 ⇒ import_kind=corrected_resubmit；有生产事实的构件禁止自动覆盖（conflict 必须人工决策） |

另需非空（NOT NULL 级别）的核心事实键：所有事实/事件行的 actual_component（涉及构件的）、subproject、occurred_at（发生时刻可补录但必须有）、recorded_at、操作人；源单外键（任务→构件/工序、消耗→批次/零件、快照→构件/发运）。具体在第二阶段逐表定。

## 13. 数据冗余与事实源

原则：**外键 ID 是事实源；名称类字段默认不冗余；冗余只用于三类正当用途——快照冻结、性能聚合、导入原始值留存。**

| 数据 | 事实源 | 允许冗余处 | 冗余性质与不同步规则 |
|---|---|---|---|
| project_id / subproject_id | main_project / subproject 主表 | 几乎所有业务行直接持 subproject_id（归属键） | 事实键，永不变更（项目不允许改父级；若误建走更正） |
| 项目名/子项目名 | 主数据表 | shipment_snapshot、对外单据 | **快照值**，允许与当前主数据不同（发运后改名不改历史单据） |
| component_no / 显示构件编号 | component_list_item / actual_component | 报工、检验、装载史、快照 | 业务键冗余（稳定、不可改）；名称类仅在快照冻结 |
| 班组名称 | team | 历史事实行可留班组快照名 | 班组改名不改历史；统计按 team_id |
| 人员姓名 | employee | 报工/检验行可留姓名快照 | 改名不改历史，按 employee_id 关联 |
| 材料名称/规格 | material | 消耗/库存/需求行 | 主数据键为准；规格若按批次实测差异，以批次实测为事实 |
| 图纸名称/版次号 | drawing/revision | 绑定行、变更影响行 | 版次号是事实的一部分，不随后续改版变化 |
| 托盘/箱号 | pallet/container | 装载史、快照 | 箱循环复用：历史按"资产ID+当时箱号"保存 |
| 重量（发运时点） | 称重/完工度量事实 | shipment_snapshot.weight | **冻结快照值**，与后续重新称重无关 |
| 子项目简称（标签展示） | subproject | QR 标签渲染时实时取，不入库或仅缓存 | 非快照，不允许手工分叉 |

红线：
1. 冗余**名称**只允许出现在"快照/对外单据/打印件"；日常业务页面一律关联取当前名。
2. 冗余**ID 归属键**（subproject_id 等）是设计的一部分，不算重复数据。
3. 计划进度、库存余额等**可重建聚合值**允许物化（plan_progress_snapshot、stock_balance），但必须能由事实重建，并标明刷新口径；它们不是事实源。
4. 任何冗余字段在详细设计时必须注释"事实源/快照/聚合"三种属性之一。

## 14. 幂等与并发设计原则

### 14.1 幂等（手机扫码第一入口）

需要幂等保证的操作：**扫码报工、检验提交、托盘装入/移除、集装箱装柜/卸柜、发运确认、状态变更（暂停/恢复/取消/项目状态）、材料消耗提交、过磅登记**。

机制（领域约定，不涉及实现）：
1. 客户端每次"提交类"操作携带**幂等键（client_token）**：同一操作人+同一终端会话+同一业务动作的重试复用同一键。
2. 服务端对幂等键唯一登记：首次执行业务并落结果；重试请求直接返回首次结果，不产生第二条事实。
3. 除幂等键外，再设**业务防重唯一键**兜底：
   - 报工：(task_id, attempt, 报工业务序号) 或到件到工序的完成事实唯一（是否允许多次部分报工为操作配置；允许时每段需有客户端行号）；
   - 装载：当前有效装载对构件唯一（重复装入同托盘=无状态变化请求，拒绝/幂等返回；装入别的托盘必须先移除）；
   - 检验：(构件, 检验类型, attempt) 唯一；
   - 发运确认：(shipment_id) 确认动作幂等（重复确认不产生第二份快照）。
4. 网络超时语义：客户端"未收到响应"时只能用同一幂等键重试，不允许新建提交。

### 14.2 并发

1. **乐观并发**：A 类聚合根（actual_component 当前状态、pallet、shipping_container、production_task、equipment）带行版本号；两个终端同时扫同一构件时，后提交者版本不符→服务端重新读取并按状态机判定（成功/冲突提示），绝不允许后写静默覆盖。
2. **关键互斥场景**：
   - 同一构件同时被装入两个托盘：当前装载唯一约束+装载事务内锁定构件行；
   - 托盘装柜与托盘拆出并发：锁托盘聚合根，按事件顺序串行；
   - 发运确认与卸柜并发：发运事务锁定本批发运范围（箱/托盘/构件），确认期间禁止移动；
   - 超重校验与继续装载：在同一装载事务内聚合，防止"边称边装"漏判；
   - 计划调整与报工并发：两者操作不同实体（版本表 vs 事实表），天然不互斥；但新建计划版本瞬间对在途报工归属哪个版本，由服务层按"报工 occurred_at 与版本生效时间"口径确定（口径技术自决并文档化）。
3. **状态竞争**：所有状态迁移必须"先读当前状态→校验允许迁移→写入新状态+事件行"在同一事务完成。

## 15. 事务边界（按业务动作，不搞超级事务）

| 业务动作 | 同一事务内必须完成 | 明确不在同事务 |
|---|---|---|
| 清单生成实际构件 | 按 quantity 批量生成 actual_component + 各自 qr_code_registry + 从 BOM 模板实例化 part_instance（分批小事务，如每 N 件一提交） | 采购、库存等后续环节 |
| 导入套料结果 | 导入批登记 + 批次 + 明细（含零件/母材校验）整体提交或整批失败 | 实际切割（另一下料动作事务） |
| 下料切割 | cutting_record + result_line + material_consumption + 余料/废料 + 库存流水 + 零件实例状态推进 | 报工（若业务上分开扫码，可两事务，通过任务/消耗关联） |
| 派工 | 任务生成（按路线批量，分批提交）+ 初始事件行 | 计划版本变更 |
| 报工提交 | report + worker + measure + 任务状态推进 + 构件聚合状态更新（+幂等登记） | 计划数字（计划永不被回写）；质量结论 |
| 检验提交 | inspection + defects + 构件质量状态 +（不合格时）NCR 关联；返工指令若同屏确认可同事务建新 attempt 任务 | 老任务/老检验不变 |
| 托盘装入/移除 | 装载当前关系 upsert + 装载历史行 + 托盘重量聚合/超重判定 | 集装箱操作 |
| 重新包装（换托） | 旧托移除史 + 新托装入史 + 当前关系，一个事务 | |
| 集装箱装柜 | 箱当前关系 + 装柜史 + 主项目一致/混装授权校验 + 箱重超重判定 | |
| 发运确认 | 快照逐构件生成 + 发运状态 confirmed + 箱/托状态 + 事件行（锁定全部涉及对象） | 运输节点（后续独立事务） |
| 设备故障登记 | event + impact 关联任务 +（自动）异常事件生成 + 受影响计划标识 | 计划调整（须独立走调整流程） |
| 工程变更处置 | 变更影响行（状态快照）+ 处置结论（+可选返工指令） | 不自动修改计划、不删除在制任务 |
| 更正审批生效 | 原事实标记（冲正标记）+ reversal_record + 更正/重做事实 + 下游联动标记 | 申请与审批是不同事务 |
| 项目状态迁移 | 当前状态更新 + 状态史行 | 不级联改写业务事实 |
| 盘点差异处理 | 盘点单审核 + 库存流水调整行 | 异常事件可同事务或异步生成（详细设计定） |

## 16. 索引设计原则（只定维度与场景，不写 DDL）

| 索引维度 | 支撑的查询场景 |
|---|---|
| actual_component(subproject_id, component_no, instance_sequence) | 清单→构件展开、编号定位（唯一索引承载唯一约束） |
| actual_component.qr_code | 现场/车间扫码秒级解析（全局唯一） |
| actual_component 的当前生产状态/质量状态 + subproject_id | 驾驶舱状态分布、待检/在制/合格清单 |
| component_list_item(subproject_id, component_no) | 导入校验、清单查询 |
| part_instance(actual_component_id)、part_instance(material 消耗关联) | 正反向追溯 |
| material_batch(炉批号)、(supplier_id, heat_no) | 质保反查、按炉批追构件 |
| nesting_detail(material_batch_id)、(part_instance_id) | 计划链查询（批次→计划零件；对比实际）；实际追溯走 material_consumption(material_batch_id, part_instance_id)（R2-01） |

| production_report(task_id)、(execute_team_id, occurred_at)、(actual_component_id) | 计件/执行工作量统计、追溯 |
| quality_inspection(actual_component_id, attempt)、(结论, occurred_at) | 质量履历、一次合格率/最终合格统计 |
| equipment_impact(task_id)、equipment_event(equipment_id, occurred_at) | 设备影响链、停机分析 |
| pallet_load/history(actual_component_id)、(pallet_id) | 构件当前位置、托盘内容 |

| shipment_snapshot(shipment_id)、(actual_component_id)、(container_id) | 发运核对、现场扫码查发运 |

## 17. 数据权限领域模型

### 17.1 模型结构

- **RBAC 链**：user_account → user_role → role → role_permission → permission。permission 目录内含两类：
  - 功能权限（能否进入某模块/动作，如"报工提交""发运确认""计划调整"）；
  - 操作权限五档：查看 / 执行 / 修改 / 审核 / 管理。
- **数据范围（data_scope_policy）独立于功能权限**，五档：公司 / 主项目 / 子项目 / 班组 / 个人负责范围；授权可授给角色或用户，并可挂具体范围值（哪些主项目、哪些班组）。
- 一次访问的放行条件 = **功能/操作权限通过 ∧ 数据范围覆盖目标数据行**；两者都在**服务端**判定，前端隐藏按钮仅为体验。
- 初始 11 角色是可维护配置，不硬编码进结构；未来新增角色只增配置行。
- segregation_rule 表达职责分离（如同一人不能同时是过磅录入与磅差审批等），服务端在审批/提交点校验。

### 17.2 数据范围如何落到查询

| 范围档 | 可见数据边界 |
|---|---|
| 公司 | 全部主项目 |
| 主项目 | 授权集合内的 main_project 及其全部子项目与业务行 |
| 子项目 | 仅授权 subproject 的业务行（主项目汇总对其不可见或脱敏，按配置） |
| 班组 | 主责或执行关系指向本班组的构件/任务/报工（按页面口径选择，不混用） |
| 个人 | 本人作为报工人/责任人/处理人的行 |

- 业务行均有稳定归属键（subproject_id；任务/报工有 team_id、人员 id；构件有主责 team），保证范围过滤可在查询层落地，不需要 JSON 标签。
- 扫码反查（QR）走同一套范围校验：扫到范围外构件时返回"无权查看"而不是数据不存在（具体提示策略技术自决）。
- 管理类动作（项目关闭/重开、跨主项目混装授权、管理员级操作）要求"管理"档；**任何档位都不授予裸改原始事实能力**——事实更正只能走更正流。

### 17.3 与业务事实的关系

- 权限判断不写入业务事实表（不报工行存"谁有权改"这类字段）；授权变更通过配置+审计体现。
- 审批人、操作人是业务事实（写在各事件行），与"有没有权限操作"是两件事。

**无。** 第六轮冻结规则内部自洽；前五轮与第六轮的差异（如七态→八态、四权限→五权限、N-10/N-23 旧待确认表述）均已在建模时按第六轮口径采用，未发现需要回报业务方裁定的矛盾。

## 21. 架构审查整改增补（2026-09-17《整改指令 V1》：18 RED + 10 ORANGE）

> 本章为整改后新增规则收口；完整叙述（原问题→修正→最终规则→原因→验证）见 `docs/v1.2_architecture_review_resolution.md`。前文正文已同步修正全部冲突点；本章与前文共同构成当前唯一有效规则。

### 21.1 数量展开链（RED-01）

- 清单 `quantity = N` → N 行 actual_component（一件一行，无 quantity）；模板行 `qty_per_component = M` → 每个实际构件 M 行 part_instance。
- 总实例数 = Σ(清单行 quantity × 生效 BOM 各模板行 qty_per_component)。示例：需求 9 件 × 某零件每件 4 件 = 9 actual_component + 36 part_instance。

### 21.2 part_instance 身份与生命周期（RED-02/03）

- 身份：part_instance_id 全局唯一；业务唯一键 (actual_component_id, bom_template_line_id, instance_sequence)；origin_part_no 只读快照；**禁止 (actual_component_id, part_no) 唯一**。
- 生命周期：`planned → material_assigned → cut → consumed_assembled`，旁路 `scrapped / substituted / cancelled`；被替代实例永久保留、不进完工统计、经 replacement_of 建 lineage。

### 21.3 套料与消耗分离 + 守恒 + 余料链（RED-04/05/06）

- 套料（nesting_detail）≠ 库存扣减；库存账只由过账动作（领用/消耗过账/退料/盘盈亏）产生；取消/重套不碰库存账。
- **R2-01 修正**：nesting_detail 为**计划层**事实（哪批材料被计划用于哪些零件）；**实际材料来源唯一权威 = material_consumption**（实际来源必须：material_batch｜surplus_material；计划引用 planned_source_ref 可选；计划≠实际时两事实并存 + substitution_reason，原计划不覆盖）；零件允许无套料计划直接实际加工（补件/散件/直发件）；追溯主链已改为 批次/余料→material_consumption→part_instance→构件（第 2 章主线、4 章关系 29/29a/29b、5 章、12 章约束 16/21、16 章索引、20 章风险 12 同步）。
- 守恒：投入 = Σ有效消耗 + Σ废料 + Σ余料 ± 容差（换算/称重/舍入/理论-实际差异；软校验超差进异常中心）。
- 余料链：原始批次 → 余料（带 source_batch_id）→ 再消耗 → part_instance → 构件；成品可反查原始批次（双向追溯用例不变）。

### 21.4 报工唯一语义（RED-07）

- production_report = 单次作业事实（非增量申报/非最终申报/非状态声明）；工时=Σ(duration)；完成数量=COUNT(到件行)；task.status 只由生命周期事件迁移。

### 21.5 工序实例与 attempt（RED-08/10）

- 任务唯一键 (actual_component_id, route_template_step_id, attempt)；同一 operation_type 出现两次 = 不同 step = 不同任务（独立计划/报工/质量/attempt）。
- 返工链：attempt1 任务 → 检验 failed → NCR 原因 → attempt2 任务（rework_of）→ 复检 → 最终结论。

### 21.6 完成/合格/可发运（RED-09）

- production_completed、final_qualified 相互独立；releasable = 两者同时成立 ∧ 非 scrapped/冻结（服务层推导）；shipped 为发运快照事实。不合格构件禁止进入包装/发运。

### 21.7 报废/补件/替换不膨胀（RED-11）

- 需求数量恒 = 清单 quantity；补件实例带 replacement_for；完成 = COUNT(有效实例)；报废 = COUNT(scrap_record)。lineage 原则同样适用于零件替代、材料替代、返工替换。

### 21.8 计划版本与在途任务（RED-12）

- 版本只追加、旧版冻结可追溯；日期/优先级/班组可在新版调整；数量/工序/粒度变化必须新版本；已执行事实永不被新版本覆盖；超量实例走取消/报废流程。

### 21.9 构件清单导入过程域（RED-13/14）

- 新实体：component_list_import_batch / component_list_import_error / import_field_mapping（见 3.3 域）；流程：文件→批次→sheet 检测→表头识别→字段映射→校验→预览→批准→正式导入→结果。
- 幂等：**(subproject_id, file_hash, mapping_version)** 唯一；失败语义默认部分成功（partial_success 批次状态+失败行明细+修复重传），`strict_all_or_nothing` 配置可切全有全无。**OPEN-1：A/B 模式需业务确认**（默认 B，不阻塞详设）。

### 21.10 字典与字段归属（RED-15/16/17）

- component_type 正式字典 + component_feature 特征标签（承接"备带抗剪键"类值）；导入映射版本化，映射失败→未分类+人工归类留痕；禁止 remark LIKE 统计。
- Excel"制作班组"= 初始主责班组**计划值**（导入快照 + primary_team_assignment 初始建议），≠ 执行班组 ≠ 实际人员；"外协"类值字典标记。
- 11 个真实字段归属表见 resolution 文档 RED-17（编号/规格/长度/材质→构件主数据；数量→清单事实；单重→清单理论重；总重→导入原值+复验；表面积→理论值；类型→字典；班组→主责建议；备注→原文快照）。

### 21.11 重量语义收口（RED-18）

- 清单单重 = 单件理论计算重（导入事实）；清单总重 = 计算值（导入原值+复验双存，真实数据存在舍入差）。
- 链条：清单理论重 → 构件理论重 → 构件实测重（度量事实）→ 发运快照重（冻结）；理论重算出版次、不回改历史。

### 21.12 ORANGE 规则摘要（ORANGE-01~10）

1. 共享库存：所有权（公司）/归属（分摊）/使用权/消耗分离；子项目角色仅见已分配行，公共池只读+申请过账。
2. 多角色：功能权限 union；事实保护类操作 deny 优先；数据范围 union；写操作服务端最严校验。
3. 幂等：client_token（UUID，重试复用）+ 双层防重不变；离线 V1 不实现但规则已立（occurred_at+token+设备号）。
4. 时间补录：≤72h 自由；>72h 原因+班组长审批；>30d 管理员+更正流程；recorded_at 恒服务器时间。
5. 设备影响：equipment_impact 人工确认（系统只建议），不自动改任务/报工。
6. 异常中心：exception_event（根因）+ exception_impact（影响对象多行），一因多果一条记录。
7. 发运双口径：事件次数口径与独立构件口径并列输出；退运/重发走新 shipment，构件状态 returned→shipped→site_received。
8. MES 边界：site_received 为终点；不推导安装、不建安装实体；MES"项目完工"=发运完成。
9. 图纸换版：受影响构件按当时状态（未开始/进行中/完成未发运/已发运）分别处置，全部留痕；新版不覆盖旧事实。
10. 盘点纠差：差异=新事实（stock_ledger 盘盈亏行+盘点单引用）；分类 normal/correction/adjustment；禁止直改余额。

### 21.16 R2 补丁整改增补（2026-09-17《第二次架构模型补丁整改 R2》）

**R2-01 计划套料/实际材料来源分离**：三层语义收口——套料事实（nesting_detail，计划）／实际切割事实（cutting_record+result_line）／实际消耗（material_consumption，实际扣减与实际来源权威）。反查构件材料来源唯一路径：`actual_component → part_instance → material_consumption（实际来源必须）→ material_batch`；nesting_detail 不作为实际炉批依据。计划=实际与计划≠实际两种情况均合法并存，原计划历史永不覆盖。零件无套料直接加工**允许**（补件、散件/直发件、小批量场景；F1 备注已有"直发件"证据），不强迫 part_instance 先有 nesting_detail。关系 29 改可选（计划）、29a/29b 新增（实际必须）。

**R2-02 replacement_for 结构化**：actual_component.replacement_for（可空自引用外键）——实体定义（3.3）、关系 86（基数 1—0..1）、约束 22（指向实例必须 scrapped/cancelled）、状态（补件实例独立走生产状态机）、统计（21.7：需求数量恒=清单 quantity，完成只计有效实例）五处闭环。示例：需求 10 件，AC05 报废 → AC11 replacement_for=AC05，需求仍=10。

**R2-03 三类替代分立**：构件替代=R2-02 自引用 lineage；零件替代=part_instance.replacement_of（自引用外键，关系 87：原件保留 substituted、替代件、替代原因、发生时间、审批引用）；**材料替代=material_consumption 计划/实际双层差异事实（关系 88），不是 lineage 字段**——首轮 21.15 中"材料 substituted_for 自引用"表述错误已废除。第一阶段排除范围：无"部件级多对多替代矩阵"（若未来出现，走工程变更域扩展）。

**R2-04 导入修正业务语义**：四概念链——source file（文件+hash）→ import_batch（一次尝试，supersedes_batch_id + import_kind）→ import_correction_result（业务净效果：created/updated/kept/conflict/rejected）→ 生效业务结果。修正导入规则：①旧批次可作废仅当其构件**全部无生产事实**；②component_no 相同∧无生产事实∧字段有变化 → 更新主数据（updated，留审计轨迹）；③无变化 → kept；④actual_component 按 (subproject, component_no, instance_sequence) 幂等复用，**不重复创建**；⑤已开工构件**禁止自动覆盖** → conflict 行人工决策（保持/走工程变更）；⑥无生产事实构件允许修正；⑦批次链永不删除，新旧文件关系由 supersedes + import_kind + 结果统计记录；⑧hash A 完全相同 → duplicate_rejected。**禁止按 component_no 简单去重**：区分修正导入（corrected_resubmit）／工程新版本（new_data_version，走工程变更+版次）／新增（created）／重复上传（duplicate_rejected）四种情况。

**R2-05 类型/特征结构化**：component_type_dict（标准类型，开放字典——新客户"次梁/框架梁"等新叫法只需加映射行与字典行，不改库结构）+ component_feature_dict（特征标签）+ component_type_mapping（来源原始值→标准值，版本化留痕）三实体落点（3.25）。真实 24 值作为映射**初始数据**而非硬编码枚举。未分类规则见 O2-02。

**R2-06 工序身份全文一致性**：三元组语义定稿——operation_type="这是哪一种工序"（分类字典）；route_template_step="这条路线中第几个工序步骤"（路线模板行）；production_task="对该构件在该具体 step 的第几次执行"。R2 扫描修正 5 处残留（3.11 实体行、4 章关系 41、12 章约束 19、16 章索引补充、21.15 失实自检更正）；operation_type 作为分类/统计维度合法保留，全文不再承担身份语义。

**O2-01 补件序号与需求位置**：physical instance sequence 保留物理发放语义（只增不回收）；AC11 是新物理实例、业务上经 replacement_for 替代 AC05；**不引入 demand_position 概念**（V1 需求槽位=清单 quantity 总数，无需逐槽位建模；若未来业务要求逐槽位表达，作为加法预留扩展，不与 physical sequence 混用）。

**O2-02 未分类 component_type 规则**：①允许导入（mapping 未命中 → 未分类标记 + 批次告警行，导入批次仍 success/partial_success）；②**不允许排产/派工**（计划展开与任务下达服务层硬拦截未分类构件）；③进入总量统计，不进入类型维度统计；④人工归类动作在 component_type_mapping 留痕后构件方可放行生产。需先确认的字段：类型归类（映射命中）——其余主数据字段按既有导入校验。

**O2-03 外协语义**："外协"= **制作来源标记（make_type: inhouse/outsource）**，不是供应商、不是班组类型本身：①班组字典带 team_type ∈ {inhouse, outsource}（外协班组仍是执行主体）；②构件制作来源 = 主责班组的 team_type 推导（可显式落 make_type 快照）；③供应商（supplier）是采购/库存域独立实体（N-4），与 team 禁止共指。一个值不再同时承担 team/supplier 两种含义。

**O2-04 重量统计配置变化**：统计口径配置（实测优先/理论优先）变更只影响**变更之后**生成的统计；历史报表已出数的以当时口径为准——若需固定，统计快照表（plan_progress_snapshot 同类的 report_snapshot）在出报时冻结口径版本与数值；历史事实行（实测重/理论重）永不回改。V1 边界：口径配置 + 出报时点口径记录为必须；全量历史报表重算引擎不做（OUT_OF_SCOPE）。

**O2-05 验证分层**：**架构规则已成立（RULE CLOSED）** vs **真实生产数据已验证（VALIDATION_PENDING）**两概念分离，RED-02/03/04/05/06 与 R2 各项的分层状态见 resolution 文档 R2 章节的状态列；真实 BOM/套料/消耗样本到位前，任何"已验证"只指规则层。

**R2 新增 OPEN**：**OPEN-4：导入修正时"updated 更新哪些主数据字段"的白名单**（component_no/数量/重量等哪些允许 updated、哪些必须走工程变更）——当前规则为"无生产事实可 updated"，字段级白名单需业务与深化设计确认；不确认风险：修正导入可能静默修改本应走变更的工程数据（有审计轨迹兜底，可回滚）。OPEN-1/2/3 维持。
