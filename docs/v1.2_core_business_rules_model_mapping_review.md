### 2.2 结论摘要

1. **48/60 规则已被当前模型结构正确支撑**，其中导入修正链（R2-04）、三类替代分立（关系 86/87/88）、工序身份三元组（R2-06）、历史事实只追加、幂等双层防重、双时间戳、守恒原则（21.7）、共享库存三分离（21.12 ORANGE-01 + 关系 14）等高风险区结构完整。
2. **存在 5 条 MODEL_CHANGE_REQUIRED（真实结构缺口）**：
   - **R09（MCR-1）**：`route_template / route_template_step`（含 `bom_template_line` 行级）**无不可变约束或版本化**，生产任务以模板行 ID 为锚，行内容可变 = 历史生产事实的工程定义锚点漂移；
   - **R27（MCR-2）**：`surplus_material` **无父子血缘自引用**（关系 33 仅有 `material_batch → surplus_material`，"父余料→分割→子余料"断链，且与关系 33 自述"来源/去向双向可查"承诺矛盾）；
   - **R36（MCR-3）**：`make_type` 快照**无字段落点**（O2-03"可显式落快照"为 prose）；原始值留存落点缺失（与 R41 同根，统一由 MCR-4 结构承接）；
   - **R41（MCR-4）**：**成功导入行无行级原始值留存**（`import_error` 原始快照仅覆盖失败行；21.10"导入快照"无结构支撑）；
   - **R34（MCR-5，本版新增）**：库存侧**无任何"预留"结构**（无预留实体、无预留数量维度、stock_ledger 八类动作不含预留/释放），需求侧抵扣标记为计划层关系、无法表达"预留→硬占用"两段式。
3. **1 条 VALIDATION_PENDING（R25）**：证书-批次当前为 N—1（支持"一证多批"），"一批多证"结构上不可表达；真实业务是否存在该场景无资料可证，**不因此判模型错误**。
4. **0 条 DO_NOT_COPY**：上一版将 R33/R34 判为 DO_NOT_COPY 属**分类错误**——两条均为本轮总则正式规则，不得以"V1 暂无场景"降格处理。纠偏结果：R33 经补充核对 21.12 ORANGE-01 判 **COVERED**；R34 经结构穷举确认无预留表达，判 **MODEL_CHANGE_REQUIRED**。详见 2.3 与第 8 章。
5. **PHASE_2_READY = NO**（存在未解决 MODEL_CHANGE_REQUIRED，见第 10 章）。

### MCR-1 ｜ R09 工程定义历史快照/版本锚定

**问题的本质（不是"禁止 UPDATE"）**

需要保护的是：**某个实际生产任务/实际构件一旦开始生产，必须能够确定当时使用的工程定义版本；后来主数据修改不能让历史生产事实漂移。**

当前模型的锚定现状分三侧，差别很大：

| 定义侧 | 当前锚定方式 | 是否漂移 |
|---|---|---|
| 图纸 | `engineering_binding` → 指向**具体 drawing_revision**（历史版本只追加） | 不漂移 ✅（已有正确范式） |
| BOM | `part_instance` 溯源 → `bom_template_line` 行；模板头"随图号版次" | **行内容可编辑 → 漂移**；版次机制仅为 prose，行级无约束 |
| 工艺路线 | `production_task` / `production_plan_line` → **route_template_step 行 ID**（关系 38/41、约束 19） | **行内容可编辑 → 漂移**：行内"工序/顺序/默认作业要求"被改后，历史任务"当时做的是哪步、什么要求"的解释锚点跟着变 |

**候选方案比较**

| 方案 | 内容 | 评价 |
|---|---|---|
| A：版本化 | 引入路线模板版本头（如 route_template_version），任务/计划行锚定版本内步骤行；BOM 版次推进=新行集 | 更"完整"，但新增实体+任务身份多一层版本维度——对 V1 低频修改的**配置数据**是过重结构 |
| B：不可变行（停用式演进） | 模板行**禁改禁删**（已产生任务/计划行/实例的行）；修改工艺 = 新增行 + 停用旧行（行留档）；BOM 新版次 = 新行集，旧行集只读 | 生产事实继续锚定**行 ID**，行永不变 ⇒ **行 ID 即当时版本快照**——与图纸域"binding 锚定不可变 revision"同一范式 |
| C：生产事实写值快照 | 任务/报工冗余工序名称、作业要求等值快照 | 否决：冗余不可靠、丢关系语义（步骤顺序/关联），且违背 13 章"冗余最小化" |

**最终明确：方案 B 是最小结构变化。** 理由：

1. **零新增实体**——不建版本表、不建审计表；复用现有"生产事实锚定行 ID"结构，只把"行不可变"写进约束体系（11 章删除与作废策略 + 12 章约束表）；
2. 与图纸域已被验证的范式（drawing_revision 只追加 + binding 锚定 revision）**同构**，模型内部一致；
3. BOM 侧几乎零成本——模板头"随图号版次"已有版本语义，只需把"版次推进=新行集、旧行集只读"从 prose 变为正式约束；
4. 路线模板行若需显式停用标记，至多补 1 个状态标记（active/deprecated），无其他字段；
5. 不为"不可变"引入机械审计结构——11 章的删除/作废策略 + operation_log（已有）已覆盖"谁改的"留痕需求。

**不修改的后果**：模板行被编辑后历史任务/实例的工程定义语义漂移且不可审计；R09 违约；OPEN-3（BOM 样本验证）所担心的"变更后新旧记录对不上"在生产期真实发生时无法解释。

**留裁决**：方案 A vs B 的最终取舍。

### MCR-2 ｜ R27 余料父子血缘

**问题本质**：余料链路有两段——`原材料 → 切割 → 余料`（第一代）与 `父余料 → 分割 → 子余料`（二代及以上）。当前模型第一段已闭环，第二段断链。

**当前已有结构（逐段核对）**

| 链路段 | 当前结构 | 结论 |
|---|---|---|
| 原材料 → 切割 → 余料 | `cutting_result_line`（实际产出零件/消耗重量/**余料**/废料）+ 关系 33（`material_batch → surplus_material` 1—N，余料带来源批次）+ `nesting_batch` 关联 | ✅ 已闭环 |
| 余料再利用 | 关系 29b（`material_consumption → surplus_material`，余料作为实际来源被领用） | ✅ 已闭环 |
| 父余料 → 分割 → 子余料 | **无**：关系 33 只有 batch→surplus 单向；无 `surplus_material` 自引用 | ❌ 断链——子余料来源只能挂原始批次，"由哪块父余料分割"不可表达；关系 33 自述"来源/去向**双向可查**"无关系行支撑 |
| 余料 vs 废料 | `surplus_material`（可再用）与 `scrap_record`（废料事实）两实体分立（3.5） | ✅ 已严格区分，无需修改 |

**最小结构：是的，只需要一个自引用。**

- `surplus_material.parent_surplus_id`（可空自引用 → 被分割的父余料）：
  - 空 = 第一代余料，来源=材料批次（关系 33 照常）；
  - 非空 = 二代及以上余料，直接来源=父余料。
- 配套一条来源语义规则：`source_batch`（关系 33）**恒保留**（终极原材料可追），`parent_surplus_id` 表达**直接来源**——两者并存，"原材料→…→任意代余料"全链可追。
- 不需要为"分割"动作新增事件实体：父余料被消耗时已有 `material_consumption` 行（关系 29b），子余料的 `parent_surplus_id` 指向该父余料即可重建分割事实；可选增强（非必需）：cutting_result_line 允许引用父余料作为切割母材语境——留第二阶段。

**不修改的后果**：二代余料断血缘，余料再利用率/成本/质量追溯失真，违反 R27 与关系 33 自身承诺。

**留裁决**：是否 V1 即采纳（成本极低、收益明确，T 倾向采纳）；与已保留决策点②（余料与批次同表多态 vs 独立表）联动——无论哪种建模，父子自引用都缺。

### MCR-3 ｜ R36 生产主体标准化 + source_raw_value

**问题本质**：真实 Excel"制作班组"列混合公司名/人名/"外协"（NAP-2，9 种原始值）。需要回答四个落点问题，且关键判断是：**原始值到底属于导入来源快照，还是属于生产事实快照？**

**四个落点的最小方案**

| 问题 | 最小方案 | 依据 |
|---|---|---|
| ① 标准化后的生产主体存哪 | **不新增**——`primary_team_assignment`（构件当前主责，已有）+ `team.team_type`（inhouse/outsource，已有）+ `supplier`（独立实体，已有）；人名型/公司名型班组的归类经 NAP-2 映射规则落到 team 字典 | O2-03 三实体分立+禁共指已立 |
| ② make_type 存哪 | **`actual_component.make_type`**（新增 1 个快照字段，枚举 inhouse/outsource）：导入映射/首次主责指派时落值，**此后不随主责变更回写** | make_type 是构件级事实（这个构件是谁做的），不能挂在可变更的"当前主责"上——否则主责变更后外协/自制口径漂移；O2-03"可显式落快照"即此意 |
| ③ source_raw_value 存哪 | **统一落在导入来源快照（MCR-4 的导入行级结构），不在生产事实表增加任何原始值字段** | 关键判断的答案：**原始值属于导入来源快照**。理由：原始值是"来源 Excel 怎么写的"这一来源侧事实，不是生产侧事实；生产事实（构件/指派）只存标准化值+指向来源的引用（经 import_batch+行号可回查原文）；若把原始值散落到各业务表（清单行加班组原文、类型原文、备注原文……）会造成字段爆炸且语义混乱——正是用户警告的"不要因为 source_raw_value 四个字就到处增加字段" |
| ④ 映射是否版本化 | **是，且已有基础**：`component_type_mapping` 已明文版本化留痕（3.25）；班组/特征值映射纳入同一版本化映射体系（来源原始值→team/feature，版本+处理人/时间留痕）；"外协"类值=字典标记（21.10） | 映射规则会随客户/文件演进，不版本化则历史导入的映射依据不可考 |

**为什么不判"原始值落生产事实快照"**：生产事实快照（发运快照 3.21、报工 execute_team 快照等）的既有设计原则是"冻结当时**业务**状态"，而 Excel 原始值是**来源证据**——证据归来源域（import 体系），业务状态归业务域；两者混放会让 MCR-4 的修正链无法统一管理原始值版本（第一次导入 vs 修正导入的原文必须按批次隔离）。

**不修改的后果**：外协/自制口径随主责变更漂移（KPI 不稳）；NAP-2 三语义解析失去数据基础；R36 的 source_raw_value 要求落空。

**留裁决**：make_type 落 `actual_component` vs `primary_team_assignment`（T 倾向前者，理由如上）；映射配置的载体细节（映射表扩展 vs 字典行）。

### MCR-4 ｜ R41 成功导入行原始值留存

**问题本质**：Excel 导入成功后，标准化数据进入正式模型，但原始 Excel 行内容仍必须可追溯——包括第一次导入和后续修正导入的每一行原文。

**现状核对（按用户四问）**

| 问 | 答案 |
|---|---|
| import batch 是否已存在 | ✅ 已存在：`import_batch`（文件+SHA-256+sheet/表头识别+映射版本+状态机+成功/失败**行数**）+ 幂等键 (subproject_id, file_hash, mapping_version) |
| import result/detail 能否保存成功行 | ❌ 不能：`import_error` 原始快照**仅覆盖失败行**（行号+原始快照+错误）；`import_correction_result` 是**修正导入的净效果汇总**（五分类行数与明细），且仅在 corrected_resubmit 时产生——首次导入（initial）的成功行**没有任何行级记录**，只有批次级行数计数 |
| 最小增加什么结构 | **一个"导入行级"实体**（下称 `import_row`，命名留第二阶段）：每次导入的每一行一行记录 |
| 是否保存 raw row | ✅ 是——**整行 raw payload（不可变）**：整行原始值组（含制作班组原文、类型原文、备注原文、全部列），而非只挑"关键列"——挑列就是"到处增加字段"的行内版，且未来想追溯的列不可预知；领域模型不定字段级结构，只定"整行原文不可变留存"原则 |
| raw value 如何与正式记录对应 | `import_row` 携带：batch_id、sheet、行号、raw payload、**处理结果 result ∈ {created / updated / kept / conflict / rejected / failed}**、错误信息（失败行）、**目标记录引用**（标准化后落到的 component_list_item / actual_component / part_instance 等）——原始行↔正式记录双向可查 |

**与 R43/R44/R45 导入修正机制不冲突的验证推演**

1. 第一次导入 500 行 → 500 行 `import_row`（result=created，目标记录引用回填）；
2. 修正版再导入 → 新批次 import_kind=corrected_resubmit、supersedes_batch_id 指向原批次（R43）；
3. 逐行处理：已存在构件按约束 23 以 (subproject, component_no, instance_sequence) **幂等复用、不重复创建**（R44）→ 对应行 result=updated/kept/conflict/rejected；真正新增的构件=result=created；
4. **知道哪些原始行被修改**：修正批次的 import_row 明细即逐行处置结果；可选增强（非必需，留裁决）：`import_row.corrected_from_row_id` 可空自引用指向上一批次对应行，形成显式行级血缘；
5. **两版原始值都可查**：第一次导入原文在批次 1 的 import_row，修正版原文在批次 2 的 import_row——按批次隔离、互不覆盖（R41 本义）；
6. **不产生重复业务事实**：约束 23 幂等 + 五分类语义（R44）不变——import_row 是**过程记录层**，不改变业务事实的产生规则；
7. 失败行级重试（R45）：failed 行重试 = 同批次内行级重处理，import_row 状态更新即可，无需整批重跑。

**与 import_error 的关系（二选一，留裁决）**：a) `import_row` 统一承载全部行（成功/失败/修正），`import_error` 并入为 result=failed 行的属性——结构最干净，一处看全批次；b) 保留 `import_error` 不动、`import_row` 只记成功行——改动最小，但行级记录分两处、修正导入的行级语义割裂。T 倾向 a（统一行级），因为 R43/44/45 的修正语义本就按行表达。

**不修改的后果**：成功行原始值永久丢失不可重建；R41 违约；R36 的 source_raw_value 无落点；NAP-2/NAP-3 的解析与审计无证据基础；导入纠错无法回溯原始行。

**留裁决**：统一 import_row vs 与 import_error 并存；是否加 corrected_from_row_id；raw payload 的载体形式（第二阶段）。

### MCR-5 ｜ R34 预留与硬占用分开（本版新增）

**问题本质**：R34 要求"可以先预留，再在必要时形成硬占用"。当前库存侧没有"预留"这个概念——不是规则文字缺失，是**结构缺失**：

- `stock_balance`：物料+批次+库位的余额，**无预留数量维度**；
- `stock_ledger`：八类动作一本账（入库/领用/退料/调拨/盘盈盘亏/余料入池/余料领用/其他），**无预留/释放预留动作**；
- `material_requirement_item` 的"是否抵扣在途/余料"：**需求侧计划层**的"需求↔来源"对应标记——库存侧不知情，两个需求可同时抵扣同批料（先到先得领用），既不是软锁也不是硬占用。

**最小方案（不引入 ERP 级预留模块）**

- 新增**轻量 `material_reservation` 实体**：批次/库位、物料、数量（重量/张数等）、需求引用（material_requirement_item）、状态；
- 状态机：`reserved`（软预留：登记占用意向，对该需求可见）→ `allocated`（硬占用：库存侧确认，其他需求不可再用）→ `consumed`（核销：与 material_consumption/stock_ledger 领用行衔接）/ `released`（释放回可用）/ `cancelled`；
- **为什么独立实体而非扩展 stock_ledger**：预留不是库存事实（料未动），放"八类动作一本账"要改第 13 章动作定义为十类、动现有冻结语义；独立表不动 stock_balance 主结构与 stock_ledger 定义，可用量=余额−Σ(活跃预留) 的**推导值**，无冗余记账；
- **为什么独立实体而非只用抵扣标记升级**：抵扣标记挂在需求行，无法表达"同一批次对多个需求的多笔预留及其各自状态"，也无法表达与需求无关的预留（如备料）。

**不修改的后果**：无法表达软预留；多需求争抢同批料无库存侧仲裁依据；硬占用与领用核销无状态衔接，R34 两段式落空。

**留裁决**：是否 V1 实现（业务确认预留场景真实存在后启用——总则已确定采用 R34，倾向实现）；独立实体 vs stock_balance 预留维度的最终形态。

## 8. DO_NOT_COPY（成熟系统可选能力，当前 V1 不采用）

**本轮 60 条中 DO_NOT_COPY = 0。**

### 8.1 纠偏说明

上一版曾将 R33（库存所有权/使用权分离）、R34（预留/硬占用）判为 DO_NOT_COPY，理由是"V1 无对应业务场景证据"。经裁决指令纠偏，该分类**错误**：

- R33/R34 是本轮《V1.2 核心业务规则总则》的**正式规则**——总则正式规则只能按 COVERED / MODEL_CHANGE_REQUIRED / RULE_ONLY / VALIDATION_PENDING 四档判定，**不得**以"暂无场景"降格为 DO_NOT_COPY；
