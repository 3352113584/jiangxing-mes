## 0. 边界总纲

Phase 3 数据库按冻结设计将以下职责**划归应用层**（这是既定分工，不是缺口）：

1. 事务编排——"业务事实 + stock_ledger + stock_balance"三段原子性；
2. 状态机——ENUM 只保证"值合法"，**不保证"状态顺序合法"**；
3. 幂等入口——部分动作有 DB 幂等键，部分动作幂等判据由 service 层实现；
4. 冲正守卫——`aud.reversal_record` 无 DB 唯一约束（NB-P3-1），防重复依赖 service。

本文将上述责任正式固化为可验收契约。

**账务符号语义（全程适用，来源：`database_design_v1.2.md` 7.5 行 600 约定）**：

- `stock_ledger.qty_weight` 一律存**正幅值**，资金方向由 `movement_type` 表达；
- 守恒公式：入账方向（`stock_in`/`return`/`surplus_in`/`count_gain`）取 `+qty_weight`，出账方向（`issue`/`surplus_issue`/`count_loss`）取 `-qty_weight`；
- **唯一例外**：冲正行（`correction_of_id` 非空）`qty_weight` 存**反号**（原行 +30 → 冲正行 -30），与原行同 `movement_type`，凭 `correction_of_id` 参与同一守恒公式；
- 任何时刻：`stock_balance.weight_kg` == 该 (batch, location) 全部账行按守恒公式合计（H-3 已验证）。

## 一、库存事务契约（7 类动作）

### 1.0 统一事务模板（7 类动作强制遵守）

```
BEGIN（单事务，禁止中间提交）
  ① 锁定：对本次事务将触及的 whs.stock_balance 行
     SELECT ... FOR UPDATE，按 material_batch_id 升序逐行加锁
     （多批次动作必须升序，防止交叉死锁）
  ② 业务事实写入（各动作对应事实表，见 1.1~1.7）
  ③ stock_ledger INSERT（符号语义见第 0 节）
  ④ stock_balance UPDATE（原子算式：
     SET weight_kg = weight_kg ± w / pieces = pieces ± n，
     禁止先读后写覆盖式赋值；受 CHECK weight_kg >= 0 兜底）
COMMIT
```

**强制规则**：

- R-TX-1：②③④ 必须处于**同一个数据库事务**，任何一步失败整体 ROLLBACK，业务事实不得残留；
- R-TX-2：**特别禁止**"先写业务事实提交，再写库存流水"、"先改余额提交，之后补流水"等任何跨事务编排；
- R-TX-3：禁止应用层把 `stock_balance.weight_kg` 读到内存计算后整值回写（丢失并发更新）；只允许原子增量算式；
- R-TX-4：事务内出现 SQL 异常（含 CHECK 违例）必须 ROLLBACK，**禁止捕获后继续用同事务写其他数据**；
- R-TX-5：service 层不得以任何方式绕过 T-9/T-10/T-11/T-16 触发器保护（含伪造 GUC：`mes.issue_posting`/`mes.reversal_context` 仅允许在对应过账/冲正流程内设置）。

### 1.1 入库（成品上架 / 材料验收上架）

| 要素 | 契约 |
|---|---|
| 业务事实 | 成品：`prod.finished_goods_stock`（status='in_stock'）+ `prod.finished_goods_event('stock_in')`；材料：验收合格行生成 `whs.material_batch`（**不产生任何库存事实**，H-1 已验证） |
| stock_ledger | `movement_type='stock_in'`，qty_weight=+w 正幅值 |
| stock_balance | `weight_kg + w`（UPSERT，键=(material_batch_id, storage_location_id)） |
| 事务 | ①~④ 同事务；成品侧 `finished_goods_stock` INSERT 与其 ledger 行同事务 |
| 行锁顺序 | 先锁目标 balance 行；成品上架另受 `uq_finished_goods_stock_in_stock`（在库 partial unique）天然排他 |
| 失败回滚 | 整体回滚 |
| 重复请求 | 成品：以 `uq_finished_goods_stock_in_stock` 为幂等锚——service 先 SELECT 该构件在库行，命中即返回既有结果，不再写 ledger；材料批次上架：先 SELECT balance 行，已有非零在库即拒绝重复上架（走盘点流程） |
| 幂等返回 | 重复请求返回**首次上架结果**（同一 stock_in 账行/在库行引用），不产生第二笔业务事实 |

### 1.2 领料/出库

| 要素 | 契约 |
|---|---|
| 业务事实 | `whs.material_issue_document`（issue_no UNIQUE）+ `whs.material_issue_line`（单据内 line_no 唯一：`uq_material_issue_line_doc_line_no`） |
| stock_ledger | `movement_type='issue'`，`issue_line_id` 必填关联明细行，qty_weight=+w 正幅值 |
| stock_balance | `weight_kg - w` |
| 事务 | 单据+行+账行+issued_qty 刷新+余额扣减**五步同事务** |
| 行锁顺序 | balance 行升序锁 → INSERT 单据/行 → INSERT ledger → UPDATE issued_qty（T-11）→ UPDATE balance |
| T-11 义务 | `issued_qty` 刷新**必须**执行且在账行之后（同一事务）——T-11 强制账行幅值合计 == issued_qty（容差 0.001）；**禁止留空 issued_qty 绕过聚合校验** |
| 失败回滚 | 整体回滚 |
| 重复请求 | 以 issue_no 为幂等判据：service 先 SELECT by issue_no，命中即返回既有单据；并发兜底=UNIQUE 拦截后转幂等返回（见第四章 R-ID-3） |
| 幂等返回 | 第二次请求返回**首次创建的单据**及其过账结果，不产生第二张单据/第二笔账 |

### 1.3 直接消耗

| 要素 | 契约 |
|---|---|
| 业务事实 | `whs.material_consumption`（source_kind/source 批次或余料二选一，CHECK 强制） |
| stock_ledger | **两种既定模式**（冻结设计 7.9，防双重扣账）：A 领料出库模式——消耗不另出账，出库即 1.2 的 issue 行；B 直接消耗模式——账行 `movement_type='issue'` + `consumption_id` 关联。同一消耗事实**至多一条**原始出账路径 |
| stock_balance | 模式 B 中 `weight_kg - w` 与账行同事务；模式 A 由 1.2 承担 |
| 事务 | 事实+账行（模式 B）+余额同事务 |
| 行锁顺序 | balance 行升序锁 → INSERT consumption → INSERT ledger(consumption_id) → UPDATE balance |
| 失败回滚 | 整体回滚 |
| 重复请求 | **DB 级幂等键**：`client_token`（partial unique WHERE NOT NULL）——service 先 SELECT by client_token，命中返回既有消耗 |
| 幂等返回 | 同 token 重试返回**首次消耗事实**，绝不能落第二行 |

### 1.4 退料

| 要素 | 契约 |
|---|---|
| 业务事实 | `whs.stock_ledger(movement_type='return', return_reason_id=...)`——退料是**独立 movement_type**，**严禁用负数领料行冒充退料** |
| stock_ledger | `return` 行，qty_weight=+w 正幅值 |
| stock_balance | `weight_kg + w` |
| 事务 | 账行+余额同事务（退料无独立单据表，账行即事实） |
| 行锁顺序 | balance 行升序锁 → INSERT ledger('return') → UPDATE balance |
| 失败回滚 | 整体回滚 |
| 重复请求 | 当前 DB 无幂等键（冻结设计既定）。service 强制判据：请求必须携带业务引用（原领料行 id 或切割行 id），同引用已存在未冲正 return 账行时返回首次结果；**禁止无引用裸退料** |
| 幂等返回 | 重复请求返回首次退料账行引用，不产生第二笔 return |

### 1.5 余料（入池 / 出池）

| 要素 | 契约 |
|---|---|
| 业务事实 | `whs.surplus_material`（R27 血缘：source_batch_id 必填；parent_surplus_id 支持父子且 CHECK 禁自父；status: in_pool→issued/consumed/scrapped） |
| stock_ledger | 入池：`surplus_in` + `surplus_id`（CHECK 强制非空）；余料出库：`surplus_issue` + `surplus_id`（同样强制） |
| stock_balance | 入池 `+w`；出池 `-w`（出库自哪个批次-库位由余料当前所在 balance 行定） |
| 事务 | 余料事实+账行+余额同事务 |
| 行锁顺序 | balance 行升序锁 → INSERT/UPDATE surplus → INSERT ledger → UPDATE balance |
| 失败回滚 | 整体回滚 |
| 重复请求 | 入池以 `source_cutting_line_id`（或等价业务引用）为幂等判据：同引用已有 in_pool 余料即返回首次结果；status 流转（in_pool→issued）由 service 校验，禁止从 issued 跳回 in_pool |
| 幂等返回 | 重复入池返回首次余料 id，不产生第二条 surplus/第二笔 surplus_in |

### 1.6 报废

| 要素 | 契约 |
|---|---|
| 业务事实 | 构件报废：`prod.component_scrap_record`（scrap_no UNIQUE；一构件至多一次生效报废 partial unique WHERE is_effective）+ 构件状态 `production_status='scrapped'`；材料/余料报废：`whs.scrap_record`（source_type ∈ {consumption, surplus}，CHECK 强制） |
| stock_ledger | 构件报废**不产生材料库存账**（构件非库存物）；余料报废：先出池（`surplus_issue` 账行 + balance 扣减 + surplus.status→'scrapped'），`scrap_record` 与出池账行**同事务** |
| stock_balance | 仅余料报废路径扣减（经 surplus_issue） |
| 事务 | 报废事实 + （余料路径：出池账行 + 余额）同事务 |
| 行锁顺序 | balance 行升序锁 → INSERT 报废事实 →（余料路径）INSERT ledger('surplus_issue') → UPDATE surplus.status → UPDATE balance |
| 失败回滚 | 整体回滚 |
| 重复请求 | 构件报废：scrap_no 查重 + 生效报废 partial unique 双保险；材料报废：以业务引用（消耗 id/余料 id）查重，同引用已有 scrap_record 即返回首次结果 |
| 幂等返回 | 重复请求返回首次报废事实（同 scrap_no / 同引用），不产生第二次报废 |

### 1.7 冲正

**独立契约，见第二章**（守卫模式，不适用 1.0 模板①的 balance 先锁顺序——必须**先锁原记录**）。

## 二、冲正契约（F-4 守卫模式正式固化）

### 2.1 守卫流程（唯一合法冲正入口）

```
BEGIN（单事务）
  ① SELECT set_config('mes.reversal_context','on',true)          -- T-10 要求
  ② SELECT id FROM <原事实表> WHERE id=:oid AND is_effective
       FOR UPDATE                                                  -- 行锁抢资格
     → 未命中（已被冲正）: ROLLBACK，返回幂等结果（首次冲正引用），零副作用
  ③ INSERT INTO aud.reversal_record(original_ref_type, original_ref_id, ...)
       （必须先于翻转落库——T-10 校验记录先行）
  ④ UPDATE <原事实表> SET is_effective=false WHERE id=:oid         -- T-10 白名单窄路径
  ⑤ INSERT INTO whs.stock_ledger(..., correction_of_id=:原账行id,
       qty_weight= -原幅值, movement_type=与原行相同)
  ⑥ UPDATE whs.stock_balance SET weight_kg = weight_kg + 原幅值
COMMIT
```

### 2.2 强制规则

| 编号 | 规则 |
|---|---|
| R-RV-1 | ③④⑤⑥ **必须同一事务**；禁止拆成多个事务（如"先插冲正记录提交，稍后翻转"——会在 DB 留下半完成态且不被 T-10 拦截） |
| R-RV-2 | 并发请求**必须只有一个成功**：败者在 ② 的 `FOR UPDATE` 复验中落空，**零副作用返回**（F-4 实测：恰一胜、reversal_record=1、反向账行=1） |
| R-RV-3 | 失败请求不得写入任何行（含 reversal_record） |
| R-RV-4 | **禁止通过普通 UPDATE 绕过冲正流程**：is_effective true→false 必须且只能在上述流程内发生（T-10 强制 GUC + 记录先行；false→true 复活一律被 T-10 阻止） |
| R-RV-5 | 反向账行 `qty_weight` 反号、`correction_of_id` 指向原账行——禁止用 movement_type='return' 冒充冲正 |
| R-RV-6 | 冲正适用于：直接消耗、领料账行、退料、余料入池/出池等一切已落账事实；冲正后如需更正，走**新业务事实**，禁止"冲正再原样重做"以外的手工拼账 |

### 2.3 NB-P3-1 风险记录（当前开放的 NON-BLOCKER）

- `aud.reversal_record` **不存在** `(original_ref_type, original_ref_id)` 唯一约束；
- DB 层无法独立阻止重复冲正记录（F-4b 固化证据：第二条可落库）；
- 当前唯一防线 = 本契约 2.1 的 `FOR UPDATE` 守卫（应用层）；
- mes_app 对 B 类表有 INSERT 权限，NB-1 权限矩阵**拦不住**绕过 service 的直写双冲正；
- 若未来裁决追加 partial unique，属数据库设计变更，须单独走裁决流程；在裁决前，本契约 2.1 为**强制实现标准**。

## 三、生产 → 质量状态机契约

### 3.0 总纲

- 数据库 ENUM 仅保证**值合法**（非法值被 CHECK/ENUM 拒绝，d2 已验证）；**状态顺序合法性 100% 属于 service 层强制责任**（当前 DB 允许任意跳值，如 pending→completed、not_started→shipped）；
- service 每次状态变更必须：读当前值 → 校验转换在合法表内 → 同事务 UPDATE 并写对应事实/事件表（履历）→ 不在表内的转换一律业务报错；
- 状态更新与对应事实（如放行=final_qualification）必须同事务。

### 3.1 production_task.status 转换表

| from \ to | pending | in_progress | paused | completed | cancelled |
|---|---|---|---|---|---|
| pending | — | ✅ 开工 | ✅ 暂停 | ⛔ 禁止（未开工不得完成） | ✅ 取消 |
| in_progress | ⛔ | — | ✅ 暂停 | ✅ 完工 | ✅ 取消 |
| paused | ⛔ | ✅ 恢复 | — | ⛔ 禁止跳转 | ✅ 取消 |
| completed | 终态 | ⛔ | ⛔ | — | ⛔（取消事实改走 task_cancellation + need_regen） |
| cancelled | 终态 | ⛔ | ⛔ | ⛔ | — |

- 所有暂停/恢复/取消必须写 `task_event`（B 类，event_type CHECK 五值）；
- 取消必须写 `task_cancellation`（一任务至多一次，UNIQUE task_id）；
- 返工**不改原任务状态**：原任务保持 completed/cancelled，返工走 `rework_order`（源引用 inspection/ncr/engineering_change）→ 新任务 `attempt+1`、`rework_of_task_id` 指原任务（身份三元组唯一保证 attempt 递增合法）。

### 3.2 actual_component.production_status 转换表（enum_ac_production 十值）

```
not_started ──开工──▶ in_production ──暂停/恢复──▶ paused
in_production ──全部工序完工──▶ production_completed
production_completed ──成品上架──▶ in_stock ──装托──▶ on_pallet
   ──装柜──▶ in_container ──发运──▶ shipped ──现场签收──▶ site_received
任意状态 ──报废审批生效──▶ scrapped（终态）
```

| 规则 | 内容 |
|---|---|
| 由生产接口改变的 | not_started / in_production / paused / production_completed |
| 由仓储接口改变的 | in_stock / on_pallet / in_container（与 finished_goods_stock 同事务联动） |
| 由发运接口改变的 | shipped / in_container（与 shipment 事实同事务联动） |
| 由现场接口改变的 | site_received（与 site_delivery_record 同事务） |
| 由报废接口改变的 | scrapped（必须存在生效 `component_scrap_record`，partial unique 保证一补一锚点） |
| 禁止 | 任何跨段跳转（如 not_started→in_stock、in_production→shipped、production_completed→not_started）；scrapped 后一切恢复 |
| 补件 | 报废件不复活；补件=新建 actual_component（seq 不复用），`replacement_for` 指向报废件（T-2 校验指向态必须 scrapped） |

### 3.3 actual_component.quality_status 转换表（enum_ac_quality 六值）

```
pending_inspection ──QC判定──▶ first_pass | failed
failed ──返工指令──▶ reworking ──返工完成重新报验──▶ reinspection
reinspection ──QC复检判定──▶ first_pass | failed
first_pass ──最终放行──▶ final_qualified
```

| 规则 | 内容 |
|---|---|
| 由 QC 接口改变的 | pending_inspection→first_pass/failed；reinspection→first_pass/failed |
| 由生产/返工接口改变的 | failed→reworking；reworking→reinspection |
| 由放行接口改变的 | first_pass→final_qualified（**必须同事务** INSERT final_qualification 事实，partial unique 保证当前放行唯一） |
| 禁止 | pending_inspection 直接跳 final_qualified（未检验放行）；failed 直接跳 final_qualified（不合格放行）；first_pass 未放行前回退 pending_inspection |
| 历史 QC 结果 | `quality_inspection.conclusion` 一次置值后**永久冻结**（T-9）；复检**永远走新 attempt 行**，禁止改旧行——旧 fail 不阻断合法复检（j2 实测） |
| final_qualified 撤销 | 仅走 `final_qualification` 的 revoke 一次性置值（T-16，白名单仅此三列）；**普通接口禁止覆盖放行事实**。撤销后 quality_status 的处置（保持/回退）冻结设计未定义 → 见 6.2 待裁决项 FQ-1 |

### 3.4 quality_inspection.inspection_status 转换表（enum_inspection 三值）

| from \ to | registered | inspecting | concluded |
|---|---|---|---|
| registered | — | ✅ 开始检验 | ⛔ 禁止（未检验出结论） |
| inspecting | ⛔ | — | ✅ 出结论 |
| concluded | 终态（行冻结） | ⛔ | — |

- `conclusion`（pass/fail）仅允许在 status=concluded 的事务内一次置值（T-9 白名单 {conclusion, inspection_status}）；
- conclusion 已置值后**任何** UPDATE 均被 T-9 拒绝（含"同值重写"以外的一切变更）。

### 3.5 放行独立性（J-1 契约化）

- 生产完成（task.completed + production_status=production_completed）**≠** 质量放行；
- 放行唯一表达 = `final_qualification` 事实行（is_qualified, NOT revoked）；
- **放行前置条件（service 强制校验，DB 无此约束）**：该构件存在 conclusion='pass' 的检验行，且不存在生效的未撤销放行，且构件未处于 reworking/failed；
- 数据库当前**不校验**上述前置（INSERT final_qualification 仅受 partial unique 约束）——service 必须实现，违者视为契约违规。

## 四、库存幂等契约

### 4.1 幂等方式总表（逐动作，拒绝笼统）

| 动作 | 幂等方式 | DB 既有锚点 | service 判据 |
|---|---|---|---|
| 生产报工 | action_key（业务动作幂等）+ client_token（网络幂等） | `uq_production_report_task_action_key`、`ix_production_report_client_token` | 先查 (task_id, action_key) 命中→返回首次报工；report_seq 仅显示序号**非**幂等键（NB-3 三者分工） |
| 直接消耗 | client_token | `ix_material_consumption_client_token`（partial unique） | 先查 token 命中→返回首次消耗事实 |
| 领料/出库 | 单据号 | `uq_material_issue_document_issue_no` + `uq_material_issue_line_doc_line_no` | 先查 issue_no 命中→返回首次单据+过账结果 |
| 预留 | 单据号 | `uq_material_reservation_reservation_no` | 先查 reservation_no |
| 构件报废 | scrap_no + 生效唯一 | `uq_component_scrap_record_scrap_no`、`ix_component_scrap_record_effective` | 先查构件生效报废命中→返回首次报废 |
| 入库（成品上架） | 业务唯一锚 | `uq_finished_goods_stock_in_stock`（在库 partial unique） | 先查构件在库行命中→返回首次上架 |
| 入库（材料上架）/退料/余料/材料报废 | **无 DB 幂等键**（冻结设计既定） | — | **业务引用查重**：请求强制携带引用（批次+库位+来源领料行/切割行/消耗 id），service 以"同引用已存在未冲正账行/事实"判重；命中→返回首次结果 |
| 冲正 | 状态守卫 | （NB-P3-1：无 DB 唯一键） | 第二章 2.1 守卫；已冲正→返回首次冲正引用 |

### 4.2 幂等返回语义（强制）

- R-ID-1：同一请求发送两次：第一次成功，第二次**必须返回第一次操作的确定性结果**（同一业务事实 id / 同一单据号 / 同一冲正引用 + 明确幂等标识），**绝不产生第二笔业务事实、第二条账行、第二行余额变动**；
- R-ID-2：幂等判据查询与写入必须同事务（或先查后写+唯一键兜底），禁止"查完再插"之间的竞态窗口无兜底；
- R-ID-3：**UniqueViolation 不得作为正常业务幂等设计**——它只能作为并发竞态的**兜底防线**：捕获后必须**反查既有结果并按 R-ID-1 返回**，而不是把数据库报错直接抛给用户；
- R-ID-4：不同业务动作禁止共享幂等键空间（action_key 限报工、client_token 限其所在表的既有列，冻结设计未授权扩散）。
