## 1. 审查范围

### 1.1 审查对象与产出

- **审查对象**：现行仓库真实业务（8 Sheet 脱敏取证：原材料入库/出库、原材料字典 4444 条、周转物料入库/出库/字典 2283 条、委外加工入库/出库均 0 条纯模板）对 V1.2 Domain Model 的架构影响。
- **产出**：本文档。缺口候选与裁决点清单，交 ChatGPT 裁决。

### 1.2 判断原则（三防）

1. **防"把旧表合理化"**：现行仓库表是仓库人员自己形成的工作表，是现状证据，不是未来 MES 蓝图。Excel 有这个字段 ≠ MES 必须照搬；每个字段都拆解为"现状是什么 → 背后业务需求是什么 → V1.2 能否正规表达 → 是否真的需要模型变化"。
2. **防"因 Excel 不规范就自动判 Domain Model 错误"**：MODEL_CHANGE_REQUIRED 的唯一判定标准 = V1.2 现有实体/关系/键**无法表达真实业务事实**。Excel 的乱大部分是执行问题，不是模型问题。
3. **防"无样本就判模型错误"**：委外加工 0 条真实数据，只能给 VALIDATION_PENDING，不能给 MODEL_CHANGE_REQUIRED。

### 1.3 三分法口径

| 标签 | 定义 |
|---|---|
| **MODEL_CHANGE_REQUIRED** | 当前模型结构真的无法表达（真实证据 + 模型内证双向印证），需结构级最小整改——本文档只提出候选与最小整改方向，**不拍板** |
| **RULE_ONLY** | 模型结构可以表达，只缺业务规则（口径、必录项、动作约束） |
| **VALIDATION_PENDING** | 当前没有真实数据/证据证明，或属业务范围决策；不猜，列入验证待办 |

## 3. 原材料库定位

### 3.1 待判断的业务层级

> **仓库管理 → 原材料库 → 周转物料 → 其他仓储区域** 这个层级是否合理？

### 3.2 真实证据

- 现行 Excel 把"原材料字典、原材料出入库"与"周转物料字典、周转物料出入库"分成两套独立工作表（合计约 6700 行），字段结构互不相同——现状就是按**物料大类分表**的做法。
- 原材料出库带领料单号与理论重量；周转物料出库带二级分类（9 类：固定资产、配件、耗材、劳保、以旧换新、领出发项目等），二者业务语义不同但被同一"出库"概念承载。
- 成品库存现实存在（发货前存放），现行表未覆盖。

### 3.3 分析：层级在组织层合理，在领域模型层应换一种表达

1. **组织/流程层**：仓库人员按物料大类（原材料/周转物料）分管、分表记账——这个层级作为**管理分工**是合理的，真实业务就是这么运转的。
2. **领域模型层**：V1.2 的正解不是把"原材料库/周转物料"建成仓库管理下的**子系统分支**，而是：**统一库存框架（warehouse/stock_balance/stock_ledger）+ 物料分类维度（material 主数据分类）**。原材料与周转物料的差异是分类差异 + 规则差异（周转料"领出≠消耗"，见第 11 章），不是账本结构差异。若按层级树各建一套出入库，就是照搬现状分表，制造两本账。
3. **"其他仓储区域"中的成品库**：V1.2 已单独处理——finished_goods_stock（一个 actual_component 一行）/ finished_goods_event 与原料库存**分域**（风险检查第 1 项确认无重叠），但共用 warehouse/storage_location 物理结构。这证明"其他仓储区域"不需要在仓库管理下再分层级树，而是按**业务对象性质**分实体。
4. **仓库管理 vs 原材料管理职责**：V1.2 已天然分开——

| 职责 | V1.2 落点 | 域 |
|---|---|---|
| 收货、入库、库位、库存、出库、退料、调拨、盘点 | purchase_receipt 群、warehouse/storage_location、stock_balance、stock_ledger、inventory_check | 采购域 + 库存域 |
| 材料身份、规格、材质、批次 Heat、MTR、实际消耗、材料血缘、余料 | material、material_batch、material_certificate、material_consumption、surplus_material | 材料域 |

两线衔接点：material_batch → stock_balance（关系 20）——材料身份（批次）是库存的维度，不是库存的子类型。

### 3.4 判定

- **层级判断**：作为管理分工合理；作为模型结构**不照搬**——统一库存框架 + 物料分类表达，成品独立实体。
- **两域职责已分开**，原材料管理不是仓库管理的下属子系统，原材料库不需要独立"仓库子系统分支"。
- **标签：无缺口（模型方向正确，与真实病灶相反方向——现状恰是材料台账与库存台账混记导致消耗与余料算不清）。** 配套规则 R-5（材料主数据建立）。

## 4. 到货 / 收货 / 入库边界

### 4.1 四层区分核查（必须保证：到货通知 ≠ 收货 ≠ 入库 ≠ 实际消耗）

| 层 | 语义 | V1.2 落点 | 边界是否清晰 |
|---|---|---|---|
| ① 到货通知 | 货在途/已到现场未卸货验收的**预告** | **无** | —（V-1） |
| ② 正式收货 | 卸货、清点、验收结论 | `purchase_receipt` / `purchase_receipt_item`（验收结论字段） | ✅ 与③④边界清晰 |
| ③ 库存入账 | 验收合格进入库存 | `stock_ledger` 动作"入库" + `stock_balance`（批次经关系 17/20） | ✅ 收货事实 ≠ 入账流水，两层各自独立 |
| ④ 实际消耗 | 生产耗用 | `material_consumption`（RED-04：库存扣减的唯一业务依据） | ✅ 与③分属两端，链路：入库→批次→（领用/消耗过账）→扣减 |

②③④ 三层在 V1.2 中边界清晰且不重叠。**缺的只有第①层。**

### 4.2 "Excel 没有 ≠ 现实没有"

- 真实 Excel **没有到货通知字段**（原材料入库 30 列无预告类字段）。
- 用户口述是真实业务事实："上午到一车檩条（某项目）"——微信群口头通知。二者并存证明**到货预告行为现实存在，只是从未被表格承载**。
- 推论：不能因 Excel 无字段否认该环节；也不能因口述存在就推断需要大型实体。

### 4.3 分析

1. 到货通知的业务价值：提前备库位/吊装、P-17 计划联动"已采购在途"可视化、P-25 异常③"采购延期"早期信号。
2. 但 P-17 的"在途"已可由 purchase_order / po_item_allocation 推导；P-25 异常③以采购单为来源单据——**到货通知不是这些能力的必要前提**。
3. 若引入，只能是**收货前的轻量事件/记录**（谁、何时、预计什么料、大概多少、哪个项目），不含验收结论、不生成批次。
4. **设计不变量（无论是否引入都必须成立）：到货通知 ≠ 收货 ≠ 入账——到货通知不能直接增加库存，库存入账唯一入口是验收后的入库过账。**

### 4.4 判定

**V-1（VALIDATION_PENDING）**：到货通知是否作为 V1 正式业务对象/轻量事件/不进系统，三档位交 ChatGPT 连同 V1 范围裁决。**本轮不判 MODEL_CHANGE_REQUIRED**：②③④层表达已完整，①层缺失不阻塞任何既有事实链。若引入，配套规则 R-7。

## 5. 领料 / 实际消耗边界（本次最高优先级）

### 5.1 核心命题

> 仓库出库是否等于 actual material consumption？当前模型能否完整表达：库存 → 仓库出库/领料 → 现场持有 → 实际消耗 → 余料 → 废料？

### 5.2 真实证据（取证文档）

- 原材料出库表有**领料记录**（领料单号 L+日期+序号 格式，如 L260818002），7 条出库数据带手填理论重量。
- **没有可靠的实际消耗字段**——出库即从表中消失，之后用掉多少、剩多少、退多少，无任何表格承载。
- 现状结论：**领料→实际消耗→余料不能闭环**（用户确认的现实问题 + 取证核实）。
- 出库表混入"采购类型=车间退料"的行——现场存在"领出去又退回来"的回流，但退料量无法与领料量对应核算。

### 5.3 模型现状（RED-04 已裁决的概念表）

`v1.2_architecture_review_resolution.md` RED-04 五概念分立：

| 概念 | 承载实体 | 事实性质 |
|---|---|---|
| 套料计划 | nesting_batch + nesting_detail | 计划事实（不影响库存账） |
| 实际切割 | cutting_record + cutting_result_line | 作业结果事实 |
| **实际领料** | **stock_ledger（领用行）+ 领用单据事实** | 库存账动作事实 |
| **实际消耗** | **material_consumption** | 消耗事实（**库存扣减的唯一业务依据**） |
| 余料/废料 | surplus_material / scrap_record | 实物事实 |

直答核心命题：**仓库出库 ≠ actual material consumption**——V1.2 已把两者明确分开（领用行=库存账动作；material_consumption=生产消耗权威事实，必须落到 part_instance + 实际来源 batch|surplus 多态，关系 29a/29b）。这正是对本轮现实问题"领料与消耗混同"的正确回应。

### 5.4 全链六环节核查

| 环节 | V1.2 落点 | 判定 |
|---|---|---|
| 库存 | stock_balance（批次+库位维度） | ✅ |
| 仓库出库/领料 | stock_ledger 动作"领用" | ⚠️ 动作有；**领用单据落点缺（G-1）** |
| 现场持有 | —（无实体） | ✅ **不需要实体**：现场持有 = Σ领用 − Σ消耗 − Σ退料 − Σ余料入池（按批次聚合，四个减数全为只追加事实），是推导态不是记账事实；给中间态立账会引入第二本账，破坏 RED-05 守恒单向性。意向层由 MCR-5 material_reservation 补齐（reserved→allocated→领用核销） |
| 实际消耗 | material_consumption（R2-01 权威事实） | ✅ |
| 余料 | surplus_material（第 7 章） | ✅ |
| 废料 | scrap_record（与余料分立，R28） | ✅ |

**审查纪律自检**：没有因为模型里有 stock_ledger 和 material_consumption 就自动认为链条完整——逐环节核查后确认两处真实问题：单据落点缺口（G-1）与过账时序未定（V-6）。

### 5.5 G-1：领用单据事实无落点

- **证据**：真实仓库出库以**领料单**为单位（一张单多行料），领料单号是现场核算与追溯的实际凭据。
- **模型内证**：RED-04 概念表在"实际领料"行明确写了 `stock_ledger（领用行）**+ 领用单据事实**`——裁决文本自身承认领料单据是概念组成部分；但 3.7 库存域实体清单中**没有任何单据头/单据引用落点**（全文检索"领用单/领料单/出库单"无实体命中）。八类动作的领用行按动作记账，无法表达"多行流水同属一张领料单"。
- **定性**：模型与自身裁决文本之间的落差，非 Excel 牵强附会（真实证据 + RED-04 文本双向印证）。
- **最小整改方向（供裁决）**：方案 a——stock_ledger 增可选单据引用字段（单据不立实体，改动最小）；方案 b——轻量领料单头实体（单号、日期、领用班组/项目、状态）。两者均不动八类动作定义。

### 5.6 判定汇总

| 项 | 标签 |
|---|---|
| 仓库出库 ≠ 实际消耗的双事实结构 | ✅ 已具备（RED-04） |
| 现场（production_use）中间态 | ✅ 不需要实体（推导态 + 退料 + 预留三层闭合） |
| 领用单据事实落点 | **MODEL_CHANGE_REQUIRED 候选 G-1** |
| 领用/消耗过账时序（扣库存时点） | VALIDATION_PENDING **V-6** |
| 领用↔消耗↔退料按批次对账规则 | RULE_ONLY **R-1** |

## 6. 退料

### 6.1 真实证据

- 现行出库表"采购类型"枚举 = {自采购， 车间退料}；**退料行出现在出库表中**（方向矛盾：退料使库存增加，却记在出库方向的工作表里）。
- 现场确实存在领出后退回（表内无原因字段）。

### 6.2 issue / return / consumption 三分核查

| 语义 | V1.2 落点 | 判定 |
|---|---|---|
| issue（领用出库） | stock_ledger 动作"领用" | ✅ 独立 |
| return（退料回库） | stock_ledger 动作"退料"（独立动作类型，入库方向） | ✅ 独立，不与出库混记 |
| consumption（消耗） | material_consumption（**不在 ledger 内**，RED-04 分立） | ✅ 独立 |

（transfer/adjustment 亦为独立动作类型，见 2.1 表。）

### 6.3 分析：退料是"库存动作类型"还是"独立业务事实 + 对应库存交易"？

- **"车间退料"的业务本质**：现场未用完材料回库，批次身份不变、数量回加。它是库存动作，V1.2 把它作为八类动作之一表达是正确的——退料行本身就是"独立业务事实 + 对应库存交易"的合一。
- **三个必须分清的混淆**：
  a) 退料 ≠ 冲正。冲正是更正错误事实（走更正/冲正流程，产生反向行，RED-04-2）；退料是正常业务回流。真实表中两者完全混同且无冲正概念 = CURRENT_STATE_ISSUE。
  b) 车间退料 ≠ 供应商退货。后者属采购域（对 supplier 的实物退回），不进 stock_ledger"退料"动作。
  c) 退料回库材料须保持批次身份可追（回原批次余额），否则破坏 P-24 双向追溯——规则约束见 R-3。
- **是否需要退料独立单据/实体？** 现有证据（Excel 无退料单据、仅类型枚举）不足以支撑新实体；退料行携带原因与来源领用引用即可（字段级，与 G-1 同批详细设计）。

### 6.4 判定

**模型已正确区分 issue/return/consumption（及 transfer/adjustment），退料作为库存动作类型成立。** 明确**不照搬旧表"退料也记出库"的做法**——Excel 该做法属现状执行问题（CURRENT_STATE_ISSUE）。配套 R-3。

## 7. 余料闭环（R27 / MCR-2）

### 7.1 全链核查：原材料 → 切割 → 余料 → 再使用 → 实际消耗

| 环节 | V1.2 落点 | 判定 |
|---|---|---|
| 原材料来源（source_batch） | 关系 33：material_batch → surplus_material 1—N，"余料带来源批次"；**source_batch 恒保留=终极可追**（MCR-2 最小方案） | ✅ |

| 库位 | 实体定义含"公共池"；**库位/位置属性未显式声明** | ⚠️ 归保留决策点②（见 7.3） |

### 7.2 R27 是否足够？

**结构上足够。** source_batch（终极来源恒可追）+ parent_surplus_id（直接来源）双锚点，配合关系 29b 多态消耗来源，`批次→余料→再领用→再消耗→构件`全链无断点，与 MCR-2 最小方案结论一致。

### 7.3 真实痛点"余料不清楚"的病灶与对策

- 病灶在**执行层**：现行表格余料既无身份（哪块料）也无位置（在哪）也无数量凭证（多重）。模型解决身份与血缘；**位置与实测凭证必须靠规则强制**——余料入池必录实测重量/尺寸/库位（R-4），否则血缘链有了、入池数据仍是脏的。
- **余料位置的结构归属**：余料入池后进入库存账（"余料入池/余料领用"），位置可由 stock_balance 库位维度承载，也可作为 surplus_material 自身属性——属**保留决策点②"余料与材料批次的建模方式"**范畴。本轮仓库证据（A19 等库位码 + "余料不清楚"痛点）的作用是**强化该决策点必须显式裁决、且裁决必须包含位置语义**，不构成新的独立缺口。

### 7.4 判定

**R27 方案足够，未发现不足；MCR-2 维持原最小方案；补 R-4；余料位置归决策点②一并裁决（证据强化）。** 无新增结构缺口。

## 9. 重量 / 磅差

### 9.1 真实证据

- 入库：货单重量（三种公式模式并存）、进厂磅重（按车次合并过磅：车次 1 七行合并 31.95T，磅差 1.56‰；车次 2 每行一车——同列两种核算粒度）。
- 出库：重量人工填写理论值；同规格同单件重量实测不同（1.98875 vs 1.9925 T/件，与 7.85 密度理论值偏差 −0.18%~+0.45%）。
- 磅差公式：`(货单合计 − 进厂磅重) / 货单合计 × 1000`（‰）。

### 9.2 模型覆盖核查（8.3 节按业务含义分列、标明事实/计算/快照）

| 用户问的语义 | 8.3 落点 |
|---|---|
| 货单重量（declared） | 采购重量 / 供应商磅重（weighing_record 原始事实） |
| 进厂磅重（weighed） | 供应商过磅重量、厂内过磅重量（weighing_record，一到货可多次过磅——覆盖按车合并过磅现实） |
| 库存重量（inventory） | 库存重量（stock_balance，可重建余额） |
| 消耗重量（consumption） | 实际消耗重量（material_consumption，原始事实） |
| 理论重量（theoretical） | 清单理论单重/总重（原值+复验双存）、理论重量/理论需求量 |
| 余料/废料/构件/结算 | 余料重量、废料重量、构件实际重量、结算采用重量（weight_discrepancy：磅差率、处理方式、审批、结算采用口径——只登记事实与决定，不做财务） |

### 9.3 四个关键问题直答

1. **什么重量影响库存？** → **库存重量（stock_balance）**，由流水重建：入库侧以验收事实为准（purchase_receipt_item 数量/重量 + 厂内过磅），出库侧以过账行重量为准。供应商磅重、货单重量只是入库前的事实输入，不直接写余额。
2. **什么重量用于实际消耗？** → **material_consumption 的实际消耗重量**（原始事实，实测优先），受 RED-04（消耗=扣减唯一业务依据）与 RED-05（守恒恒等式 ± 容差，容差含"理论重量与实际重量差异"）约束。
3. **什么重量只是收货/结算参考？** → 货单重量（收货核对参考）、供应商磅重（验收输入）、结算采用重量（weight_discrepancy 登记口径，不做财务）。
4. **磅差到底是什么业务含义？** → 见 9.4。

### 9.4 磅差语义四候选逐一判定

| 候选语义 | 证据支持度 | 判定 |
|---|---|---|
| 收货验收差异（货票 vs 实磅） | **强**：公式就是货单重量与进厂磅重之差，发生在验收环节 | ✅ 主语义成立 |
| 计量校正（磅秤误差管理） | 无证据（无秤校准记录） | ❌ 不成立 |
| 库存调整（入账前修正） | 无直接证据；入库重量口径未在表中说明 | ❌ 不成立（并入 V-6 入库重量口径） |
| 供应商结算依据 | **无法确认**：结算列全空，磅差与结算无公式关联 | ⚠️ **VALIDATION_PENDING V-4，不猜** |

### 9.5 判定

**模型覆盖完整（14 种重量分列 + weighing_record + weight_discrepancy），无结构缺口。** "同规格单件重量不同"正是 8.3 分列设计要防的语义坍缩——理论值只作参考与容差基准，不进库存账。出库重量口径须规则收口（**R-2**：实测优先，理论值兜底须可识别，禁静默混用）。货单合计三种公式模式、磅差同列两种粒度、运费公式行号硬编码 = CURRENT_STATE_ISSUE。

### 14.1 MCR-5 归属域裁决点：material_reservation 是库存/仓库域能力，而非生产事实

**论据（裁决归 ChatGPT）：**

- **归 inventory/warehouse 的论据（本轮倾向）**：①预留锁定的对象是**库存资源**（批次/库位/数量），可用量=余额−Σ(活跃预留) 是库存侧公式；②执行主体是仓库（备料/发货确认）；③状态机（reserved→allocated→consumed/released）本质是"库存承诺生命周期"，与 stock_balance/stock_ledger 同域共存便于一致性维护；④生产侧已有完整需求表达（material_requirement_item），预留只是需求在库存侧的投影；⑤它**不是生产事实**——料未动、工序未发生，记生产域会混淆"作业事实"与"资源承诺"两类性质。
- **归 production 的论据**：触发源是生产需求，生命周期随生产任务走；归生产域便于"需求→预留→领用"业务链内聚。
- **判定建议**：**归 inventory/warehouse 域**（资源归属域优先于触发源域——与"po_item_allocation 归采购域而非各子项目"同一归属哲学），通过 material_requirement_item 外键保持生产侧引用。**此为建议非结论。**

## 19. 最终关键结论

1. **仓库管理骨架在 V1.2 已正式存在**（CURRENT_WAREHOUSE_DOMAIN：14 项检查=7 已覆盖/5 部分/2 缺失），不是空壳——Excel 的乱大多是现状执行问题，未构成"模型错"的证据；"把旧表合理化"与"因 Excel 乱判模型错"两个方向的错误均已防住。
2. **核心命题直答：仓库出库 ≠ actual material consumption，且 V1.2 已正确区分**（stock_ledger 领用行=出库事实；material_consumption=消耗权威事实+库存扣减唯一业务依据，RED-04）。"现场持有"是可按批次推导的余额态，**不需要新实体**；真正缺的只是领料单据落点（G-1）与对账规则（R-1）。
3. **材料身份主数据层有实义缺口**（G-2）：批次/消耗/库存三层键已声明，唯主数据唯一键缺失，且真实数据证明名称+规格必然合并 221 组不同材质——必须补显式身份键（独立编码或含材质组合键，形态待裁决）。
4. **到货通知**：Excel 无字段但现实存在（口述证据）；四层边界（到货通知≠收货≠入库≠实际消耗）中 V1.2 已覆盖后三层；建议按轻量事件对待且**不触碰库存**（设计不变量），是否 V1 对象化交业务确认（V-1）。
5. **MCR-2 / MCR-5 被仓库现状强化**（余料不清楚 / 领料消耗脱节+多需求争抢），结构均无需变更；MCR-5 material_reservation **建议归 inventory/warehouse 域**（锁定库存资源、仓库执行、非生产事实），裁决交 ChatGPT。
