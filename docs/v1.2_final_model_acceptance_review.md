## 1. R61 验收：purchase_receipt 与"到货车次"

### Q1 purchase_receipt 的原始语义到底是什么？

**判定：到货车次。**

当前模型原文（3.6 采购域，line 122）：

> `purchase_receipt` ｜ 到货单头（单号、到货时间、采购单）；**语义冻结=到货车次（R61）：一次到货一张单=一个车次；trip_no（车次号，可空）、vehicle_plate（车牌，可空）；一采购单→多车次（关系 15）、一车次→多材料明细（关系 16）、一车可拆多炉批（关系 17）；车次≠material_batch/Heat≠库存单位；到货预告不建实体（库存不变量见 22.8）**

配套拆分（22.8 原文）：

> 到货预告（不建实体——微信群只是通知来源，不建通知表）→ 到货车次（purchase_receipt）→ 正式收货/验收（receipt_item 验收结论）→ 库存入账（stock_ledger 入库行）→ 实际消耗（material_consumption）

即四选项中：**purchase_receipt=到货车次**；"正式收货/验收"由 `purchase_receipt_item`（line 123 原文："到货明细（数量/重量事实、**验收结论**），生成 material_batch"）行级承载；"验收入库"由 stock_ledger 入库行承载；三段分离，不混用。

### Q2 车已到厂、尚未完成清点/验收，能否表达？

**判定：能。**

- 车次头可先登记：purchase_receipt（单号、到货时间、trip_no、vehicle_plate）+ receipt_item 明细行（数量/重量事实）——此时尚未验收；
- receipt_item 的"验收结论"为行级字段，未验收=空值/待验收中间态合法（与关系 95"流水行可空引用单据行，过账前可空"同构：先单据、后过账是模型允许的中间态；V-6 过账时序待裁决亦印证）；
- 关键保证：约束 32 原文——"**批次生成唯一入口=purchase_receipt_item 验收（关系 17）**"。未验收 ⇒ 不生成 material_batch、不入账。中间态被结构强制。

### Q3 一车 5 种材料，2 合格 3 待处理，能否表达？

**判定：能。**

- receipt_item 一行一材料（关系 16：一车次→多材料明细），**验收结论为行级字段**：2 行=合格（生成 2 个/组 material_batch，关系 17 一行可拆多炉批）、3 行=待处理（验收结论未定，不生成批次、不入账）；
- 行级独立判定 ⇒ 部分合格部分待处理互不阻塞。
- 注记（非阻塞）：验收结论的**枚举值域**（合格/待处理/拒收/让步接收…）未在领域模型冻结，留第二阶段详设细化——结构已可表达，枚举属字段取值层。

### Q4 微信群通知是否仍为非正式通知来源？

**判定：是。**

原文（22.8）："到货预告**不建实体**——微信群只是通知来源，不建通知表"；约束 32："到货预告（**链外，不建实体**）"。微信群通知存在于模型链外，**不等于也不强制生成 purchase_receipt**；purchase_receipt 的创建是仓库登记动作，二者无结构绑定。

### Q5 到货预告不能改 stock_balance、不能直接产生 material_consumption——证明。

约束 32 原文（line 728）：

> | 32 | 到货预告库存不变量（R61/R-7） | **S** | 到货预告（链外，不建实体）**不产生 stock_ledger 行、不改 stock_balance、不产生 material_consumption、不生成 material_batch**；批次生成唯一入口=purchase_receipt_item 验收（关系 17） |

四项不变量逐项冻结，且批次生成唯一入口收口于验收动作——预告层在结构上无任何库存触点。

### R61 最终判断：**R61_PASS**

## 2. G-2 验收：material identity

### Q1 material 是否已有稳定内部 identity？

**判定：有。** 双层身份：①实体代理键（material 主键——material_batch/stock/consumption 等全部事实表经实体外键引用，关系 19/20 等）；②`material_code` 业务身份。3.5 域原文："material_code（**系统管理的全局唯一业务身份**，G-2：name+规格不承担唯一性——真实证据 221 组同名称同规格不同材质）"。

### Q2 material_code 是否唯一 / 稳定 / 不允许复用 / 与 supplier_material_code 区分？

- **唯一** ✅：约束 33（DB 层）："material_code 全局唯一（系统管理）"；第 5 章唯一性表 material 行 material_code 全局唯一。
- **稳定** ✅（结构层）：主数据删除策略为"软删除（停用标记），被引用后不可物理删除"（第 11 章）；事实引用走代理键，标识链不依赖 code 字符串。
- **不允许复用** ⚠️：模型未将该禁令明文写成约束。结构基础已具备（唯一约束防同码两行并存；引用走 ID，即使历史 code 停用也不与新行冲突断链）；"复用禁令+变更流程"属主数据管理规则，建议第二阶段在详设/主数据规则中固化。**计为非阻塞注记 N-1，不判 GAP**。
- **与 supplier_material_code 区分** ✅：约束 33 原文："supplier_material_code 可空可重复（来源快照，**不覆盖标准主数据**）"；3.5 域原文："与 MES 内部身份分离、不参与唯一约束"。

### Q3 被 stock/batch/consumption 引用后，material_code 还能随意修改吗？

**判定：不能"随意"修改，且结构上改码不断链。**

- 结构层：stock/batch/consumption 对 material 的引用全部是**实体代理键外键**（非 material_code），因此即使发生 code 纠错性变更，引用链与追溯链（15 节：material→batch→Heat→MTR→inventory→issue→consumption→actual_component）不受影响；
- 语义层：material_code 是"系统管理的稳定身份"，其变更应走主数据变更流程而非随意 UPDATE——流程细则属规则/详设层（同注记 N-1）。**不存在因改码导致历史事实失配的结构风险**。

### Q4 名称相同、规格相同、材质不同，能否明确识别为不同 material？

**判定：能。** 约束 33 明文"name+specification **无唯一约束**"——二者不构成身份；材质/牌号为 material 必含属性；221 组真实证据即为此落点依据。每组同名同规格不同材质 = 独立 material 行、独立 material_code。

### Q5 供应商自己的物料编码变化，是否不影响 MES 内部 identity？

**判定：不影响。** supplier_material_code 是"可空可重复的来源快照"（约束 33），仅随到货登记更新快照值；MES 身份锚定 material/material_code，与供应商编码无结构耦合。

### G-2 最终判断：**G2_PASS**（附非阻塞注记 N-1：material_code 复用禁令/变更流程留详设规则层）

## 3. MCR-4 验收：import_row

### source_identity 到底来自什么？

**明确回答：稳定业务键（业务键标准化后的结果）。**

3.3 域原文："source_identity（**稳定业务识别依据=业务键，如子项目+构件号**，幂等身份的一半）"。

排除项：

| 候选 | 是否 source_identity | 原文依据 |
|---|---|---|
| 行号 | ❌ 不是 | "source_row_number（源文件行号，**仅定位，不作幂等身份**）"；约束 29："source_row_number 不参与唯一约束（仅定位）"；14.1："source_row_number 不作幂等身份（**Excel 重排序即失效**）" |
| 整行 hash | ❌ 不是 | 整行内容指纹的角色由 **content_fingerprint** 承担（"内容指纹，修改行识别"），用于判断内容是否变化，**不参与身份判定** |
| 稳定业务键 | ✅ 是 | "稳定业务识别依据=业务键，如子项目+构件号" |
| 业务键标准化后的结果 | ✅ 是（同一语义） | 幂等键 (import_batch_id, source_identity) 要求业务键在批次内取值稳定唯一（构件侧兜底见约束 23：实例按 (subproject_id, component_no, instance_sequence) 幂等复用） |

**content_fingerprint 的边界**：只能用于"判断内容变化"（同身份下指纹不同⇒updated），**不能代替**"判断是不是同一条业务记录"（身份判定唯二依据=import_batch_id+source_identity，约束 29 原文）。

### Case A：第一次 Excel 500 行成功

500 行 import_row（result_status=created，raw_payload 留原文）→ target 软引用落 500 条业务记录。✅

### Case B：第二次 Excel 完全相同——不得重复创建业务事实

第二批次每行按 source_identity 匹配到既有业务记录，content_fingerprint 相同 ⇒ result_status=**kept**（import_correction_result 枚举：created/updated/kept/conflict/rejected，3.3 域原文）→ 不新建业务实体。双层幂等：批次内 (import_batch_id, source_identity) 唯一防同批重复行；跨批次靠 source_identity 业务匹配 + 约束 23 构件实例幂等复用兜底。✅

### Case C：第二次排序变化、内容完全相同——仍识别为同一业务记录

匹配不使用 source_row_number（仅定位）；source_identity 为业务键，与行序无关 ⇒ 同一业务记录，全批 kept。✅

### Case D：排序变化 + 8 修改 + 3 新增 + 2 失效

| 结果 | 识别机制 | 原文依据 |
|---|---|---|
| **8 条修正**（updated） | 同 source_identity + content_fingerprint 不同 ⇒ 修改行；两批 raw_payload 按批次隔离保留，历史批次链永不删除（supersedes_batch_id 批次修正链） | 约束 29；3.3 域 R2-04 组 |
| **3 条新增**（created） | source_identity 无匹配 ⇒ 新行新 target | 关系 89/91 |
| **2 条失效** | 源中消失 ⇒ **不自动删除业务实体**，经 import_correction_result 标记→人工决策（有生产事实者 conflict 强制人工，无生产事实方可失效/updated） | R2-04；约束 23；22.4 |
| **487 条保持**（kept） | 同身份+同指纹 | 3.3 域 result_status 枚举 |
| 原始版/修正版均可追溯 | 批次链永不删除 + import_correction_result 净效果 + corrected_from_row_id 逐行纠正链 | 3.3 域；关系 90 |
| 不重复创建业务对象 | 身份判定唯二依据 (import_batch_id, source_identity)；跨批业务匹配 | 约束 23/29 |

✅ 全部可表达。

### MCR-4 最终判断：**IMPORT_ROW_PASS**

## 4. G-1 验收：material_issue_document

### Case A：一张领料单 5 种材料 —— 1 个单据头 + 5 条明细

关系 93 原文："material_issue_document → material_issue_line：**1—N，必须**——一张领料单多行不同材料，经一个单头全部可达"。1 单头 + 5 行，每行独立材料/批次（关系 94：行→material_batch N—1 必须）。✅

### Case B：一行计划 10 吨，分两次实际出库 6 吨 + 4 吨 —— 一条 issue_line 对应多个 stock movement？

**判定：允许，且为明文设计。**

关系 95 原文："material_issue_line ↔ stock_ledger（领用行）：**1—0..N**——单据行与库存流水行分离，流水行可空引用单据行（过账前可空，时序 V-6 待裁决）；**stock_ledger 不持单据头语义**"。

即一条 issue_line 可对应 2 条（或 N 条）领用流水行（6t+4t 分次过账）；"0"侧=开单未过账的中间态合法。✅

### Case C：一张领料单包含正常领料 × 退料 —— 退料是否会被错误当成"领料单负数行"？

**判定：不会。**

- stock_ledger 八类动作中"**退料**"为独立动作类（3.7 域原文："入库/领用/**退料**/调拨/盘盈盘亏/余料入池/余料领用/其他"）——退料有自己的库存动作语义；
- 22.9 第 3 条原文："退料**方向恒为入库、带原因、回原批次余额、保留原材料批次身份**；退料≠历史记录冲正（更正流程）≠供应商退货（采购域）；**不沿用旧 Excel'采购类型=车间退料'混记**"；
- material_issue_line 的数量语义为领用（出库方向）凭据行，模型无"以负数领料行替代正式退料"的路径；约束 30 冻结"单据≠流水"分层；
- 确认：退料不通过 issue_document 表达，Issue 与 Return 是不同业务语义（裁决十四节范围内，未要求退料单据头）。✅

### Case D：领料单（项目 A / 某班组 / 某 batch / 某仓库库位）—— 链路 issue_document → issue_line → stock movement

| 上下文 | 承载 | 关系 |
|---|---|---|
| 项目 A | 单头 subproject 上下文（main_project 经 subproject 上溯） | 关系 96 |
| 某班组（领料对象/执行主体） | 单头对象类型+ID 软引用（team/employee，受控取值） | 关系 97 |
| 某 batch | 行级 →material_batch 必须 | 关系 94 |
| 某仓库/库位 | 行级 →storage_location 可空 | 3.7 域行 |
| → stock movement | 行 ↔ stock_ledger 领用行 1—0..N | 关系 95 |

链路完整：单头（96/97）→ 行（93/94）→ 流水（95）。✅
