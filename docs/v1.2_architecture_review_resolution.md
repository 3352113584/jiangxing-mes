## 一、RED 项整改决议

### RED-01 part_instance 实例唯一性与数量展开

- **原问题**：构件多件与零件多件的展开链缺正式定义，存在以"一行写数量"表达多件的风险。
- **最终规则**：
  1. `component_list_item.quantity = N`（七类数量之①）是**唯一合法的构件需求数量**。构件实例化时系统生成 N 行 `actual_component`（instance_sequence 1..N），**一件一行、无 quantity 列**。
  2. `bom_template_line.qty_per_component = M`（七类数量之③）表示**每个实际构件**对该零件的需求。构件实例化时按生效版次 BOM 展开生成 M 行 `part_instance`（instance_sequence 1..M，按模板行维度）。
  3. 总实例数计算规则：**Σ(每清单行 quantity × 该构件生效 BOM 各模板行 qty_per_component)**。actual_component 与 part_instance 均**严禁携带数量字段**表达多件。
  4. 权威事实源：需求数量只在 component_list_item / bom_template_line；实例数只能 COUNT 行得到。
- **完整示例（强制）**：构件 T-1 清单 quantity = 9 → 生成 actual_component #1…#9（9 行）；其生效 BOM 某模板行 Part No=P1，qty_per_component = 4 → 每个实际构件生成 4 行 part_instance → **9 个 actual_component + 36 个 part_instance**（P1）。若 BOM 另有 P2×2，则再加 18 个 P2 实例。真实数据佐证：F1 行 BF-CG-1 qty=42 → 42 个 actual_component，其每个 BOM 行按上述展开。

### RED-02 part_instance 唯一身份

- **原问题**：领域模型第 5 章旧唯一键 `(actual_component_id, part_no)` 隐含"同一构件下 part_no 唯一"——**错误**。同一构件 Part A×3、Part B×6 完全正常。
- **修正**：删除该唯一键；part_instance 身份改为：
  - `part_instance_id`：全局唯一代理键（满足"到件追溯全局可定位"）；
  - 业务唯一键：**(actual_component_id, bom_template_line_id, instance_sequence)**——sequence 在"构件×模板行"维度 1..M；
  - `origin_part_no`：实例化时从模板行复制的原始零件号快照（冗余只读，用于显示与检索，**不参与唯一约束**）；
  - 禁止仅以 `actual_component_id + part_no` 作为唯一身份。
- **真实数据验证**：F1/F2 无 BOM 样本数据（见第 0 节），本项为规则先行修正；J 场景（同构件重复 Part No）标记**待 BOM 样本验证**。

### RED-03 part_instance 生命周期

- **最终规则**：状态枚举（名称可在详设微调，语义不得变）：
  `planned → material_assigned → cut → consumed_assembled`，旁路 `scrapped / substituted / cancelled`。
  - **什么叫"存在"**：所属 actual_component 实例化时按生效 BOM 展开生成实例行（planned）；行只追加不可静默改，撤销走 cancelled。
  - **什么叫"已生产"**：cut（下料事实关联后）；零件不独立派工，其后续"完成"由所属构件的工序完成事实表达（V1 边界）。
  - **什么叫"已消耗"**：consumed_assembled——零件经装配进入构件本体；此后不再单独计零件报废（构件报废连带）。
  - **什么叫"报废"**：scrapped——报废事实行（原因/时间/批准），实例行保留。
  - **什么叫"被替代"**：substituted——替代事实建立后原实例进入该状态。
  - **替代后原实例是否保留**：**永久保留**（状态 substituted，不删除、不复用身份）。
  - **被替代实例能否进正常完工统计**：**不能**；完工统计只计有效终态（见 RED-11 统计口径）。
  - **lineage 如何建立**：新实例带 `replacement_of` 自引用指向旧实例；追溯沿 lineage 链完整可查。
- **状态迁移触发**：planned→material_assigned 由套料/领用事实；→cut 由切割结果行；→consumed_assembled 由装配/工序完成事实（服务层推导）；scrapped/substituted/cancelled 由对应审批事实。

### RED-04 套料计划与实际材料消耗分离

- **原问题**：存在"套料明细写了多少 = 库存自动扣多少"的隐式风险。
- **最终规则**：
  | 概念 | 承载实体 | 事实性质 |
  |---|---|---|
  | 套料计划 | nesting_batch + nesting_detail | 计划事实（可作废/重套，不影响库存账） |
  | 实际切割 | cutting_record + cutting_result_line | 作业结果事实（产出零件/消耗/余料/废料的现场结果） |
  | 实际领料 | stock_ledger（领用行）+ 领用单据事实 | 库存账动作事实 |
  | 实际消耗 | material_consumption | 消耗事实（**库存扣减的唯一业务依据**） |
  | 余料 | surplus_material | 实物事实（实测优先） |
  | 废料 | scrap_record（废料） | 实物事实 |
  1. **套料 ≠ 库存扣减**。库存账（stock_ledger）只由过账动作产生行：领用、消耗过账、退料、盘盈亏等；取消套料/重新套料/修改套料**不产生也不回冲任何库存行**。
  2. 消耗冲正走更正/冲正流程，冲正产生库存反向行；不存在"隐式自动扣减"路径。
  3. cutting_result_line 与 nesting_detail 允许差异（差异需说明，进异常中心）。
- **原因**：把"计划"与"过账事实"分开是守恒与审计的前提；混用会同时破坏 RED-05 守恒与 RED-14 幂等。

### RED-05 材料重量/数量守恒

- **最终规则**：对一次母材投入（材料批次维度）建立守恒恒等式：
  `投入重量 = Σ(零件有效消耗) + Σ(废料) + Σ(可回收余料) ± 容差`
  - 示例（指令原例）：6000 kg → 2500（有效消耗）+ 500（废料）+ 3000（余料）= 6000 ✓。
  - **允许容差类型**：单位换算误差、称重误差（阈值可配置，默认 ±0.5%）、四舍五入误差、理论重量与实际重量差异。
  - 守恒校验为**软校验**：超容差不拦截落库，生成异常中心"仓库异常"事件人工处理；拦截会逼出假数据。
  - **重量语义必须分列**（禁止一个 weight 字段承担全部语义）：理论重量（清单/BOM，导入事实）、计算重量（=单重×数量，计算值）、领料重量（领用事实）、实际称重（过磅事实）、实际消耗（消耗事实）、废料重量（废料事实）、余料重量（余料事实）。8.3 节 13 种重量分列表继续有效，本项补充"守恒关系与容差"。
- **真实数据验证**：F2 有 11/226 行总重与单重×数量存在 ±0.015 舍入差——证明"计算复验容差"必须存在；理论/实测分离在 F1 单重（理论）与过磅事实（weighing_record）间已分列。

### RED-06 余料完整追溯链

- **最终规则**：
  `material_batch（原始批次）→ surplus_material（余料，携带 source_batch_id + 来源切割引用）→ 再次领用/切割（material_consumption.source_kind = raw_batch | surplus）→ part_instance → actual_component`
  - 余料实体**必须**携带原始批次标识（不因入池而断链）；余料自身可成为后续消耗的"源"。
  - 反查能力（强制验收用例）：任一成品构件 → part_instance → 切割/消耗事实 →（余料链递归上溯）→ 原始材料批次 → 质保书。与第 20 章风险 12 的双向追溯用例合并执行。
  - 余料出池/再入池/降级为废料均写事实行，不改原行。
- **真实数据验证**：F1/F2 为构件清单，无余料数据；规则为先行动决，待含套料/余料的真实样本复验（不阻塞）。

### RED-07 生产报工不重复计数

- **最终规则**：`production_report` 的唯一语义 = **单次作业事实**（one work-event）：一次扫码/提交记录一次作业（人、班组快照、occurred_at/recorded_at、时长或完成量度，到件场景一件一行）。
  - **不是**增量申报、**不是**最终申报、**不是**状态声明；三类语义禁止混用。
  - 同工序多次报工（例：40 分钟 + 30 分钟 + 完成声明）：实际工时 = Σ(有效 report.duration) = 70 + 完成动作时长；完成数量 = COUNT(到件事实行)；是否返工由 attempt 与质量结论表达；不重复统计（防重唯一键 + client_token 幂等）。
  - `production_task.status` 只是任务生命周期事实的聚合当前值，**不得**与 report 同时作为独立"完成数量"来源；完成数量唯一事实源 = 有效到件报工行（COUNT），完成状态唯一事实源 = 任务生命周期事件。
- **真实数据验证**：清单数据不涉及报工；规则为模型层动决。

### RED-08 attempt 限定到实际工序

- **原问题**：attempt 若只绑整个 actual_component，焊接返工会污染切割的 attempt 序列。
- **最终规则**：attempt 绑定到**工序实例**：`(actual_component, route_template_step, attempt)`（即 production_task 的身份，见 RED-10）。
  - 焊接失败→焊接返工→再焊接：attempt 只在焊接 step 上递增；切割 attempt 完全独立。
  - 强制链路：attempt 1 任务 → 检验 failed → NCR/返工原因（七分类）→ attempt 2 任务（`rework_of` 指向 attempt 1 任务）→ 复检 → 最终结论。检验表 (actual_component, inspection_type, attempt) 的 attempt 与对应工序任务的 attempt 同源递增。
- **真实数据验证**：清单无工艺数据；规则动决。

### RED-09 生产完成 ≠ 最终质量合格

- **最终规则**：四个判定相互独立，禁止跳步推导：
  | 判定 | 事实源 | 语义 |
  |---|---|---|
  | production_completed | 任务/报工聚合（生产状态机） | 所有生产工序执行完毕 |
  | quality_pass（final_qualified） | 检验事实（质量状态机） | 最终检验合格 |
  | releasable / shippable | **服务层推导**：production_completed ∧ final_qualified ∧ 非 scrapped/冻结 | 可进入包装发运 |
  | shipped | shipment_snapshot 冻结事实 | 已发运 |
  - 构件生产完成但最终检验 failed：**不进合格统计、不可装托/装柜/发运**（包装与发运动作的服务层硬校验质量态）；放行只能经返工→复检→final_qualified，或经授权特采（走审批，V1 可配置预留）。
  - 10.2 节双状态机继续有效，本项补充 releasable 推导与拦截规则。

### RED-10 重复工序的任务身份

- **原问题**：旧唯一键 `(actual_component_id, operation_type, attempt)` 无法表达"焊接→校正→焊接"——两次焊接是不同工序步骤，不是同一工序的两次 attempt。
- **修正**：production_task 身份改为 **(actual_component_id, route_template_step_id, attempt)**。
  - route_template_step（模板工序行，含 step_no 顺序）是工序实例的权威身份；operation_type 仅是显示/统计分类。
  - 同一 operation_type 在同一路由出现两次（焊接→校正→焊接）：两个**不同任务**、独立计划时间、独立报工、独立质量结论、独立 attempt 序列。
  - **连带修正**：production_plan_line 最低粒度同步改为 (plan_version_id, actual_component_id, route_template_step_id)——同一 operation_type 两次出现为两个不同计划行（3.10 域、第 5 章唯一键、4.5 关系 38 三处已同步）。
  - 领域模型第 5 章该行已同步改写；第 12 章约束映射同步。
- **原因**：工艺现实决定"工序步骤"才是最小可执行单元；以 type 判身份会在真实路由下产生主键冲突或错误合并。

### RED-11 报废/补件/替换不使需求数量膨胀

- **最终规则**：
  1. 需求数量恒等于 `component_list_item.quantity`（配置事实），**永不**因报废/补件增加。
  2. 报废：AC05 报废 → component_scrap_record 事实，AC05 状态 scrapped，序号不释放。
  3. 补件：新行 AC11（sequence 续号）携带 **`replacement_for` = AC05**（actual_component 自引用 lineage）；AC05 属于原需求实例槽位，AC11 是替代制造实例。
  4. 统计口径：**完成件数 = COUNT(状态 ∉ {scrapped, cancelled} 的实例)**；报废件数 = COUNT(component_scrap_record)。例：需求 10 件，AC01–AC10 中 AC05 报废、补 AC11 → 有效完成 = 10（AC01–04,06–10,11），报废 = 1，**需求仍 = 10，不重复计算**；AC05 履历永久保留。
  5. 同一 lineage 原则适用于：part replacement（RED-03）、material substitution（消耗事实带 substituted_for 引用）、rework replacement（任务 rework_of）。所有 lineage 引用均为自引用外键，只追加不改写。
- **真实数据验证**：F1 尾部 BW-ZZa-1..3 序号空缺行证明"清单序号本身可断号"，构件实例 sequence 由系统发放与清单序号无关（已按 5 章规则独立）；报废/补件场景待生产期数据复验。

### RED-12 计划版本与已执行任务

- **最终规则**：
  1. `production_plan_version` 只追加；V2 = 新版本行，V1 下发后**冻结只读**，历史计划可完整追溯（谁、何时、什么内容、为何调整）。
  2. 已执行任务的归属引用指向**版本 + 计划行**；V2 发布时：
     - **允许在 V2 中调整**：日期、优先级、班组指派、目标时间——以新版本行承载，V1 原值保留；
     - **必须新建版本**：数量变化、工序安排变化、计划行增删（粒度变化）；
     - **禁止覆盖**：已开工/已完成任务的实际事实（起止、报工、质量）永不被 V2 改写；V2 与在途任务冲突时生成 plan_adjustment + 预警，由人决定是否调整任务（调整本身再留痕）。
  3. 数量调减导致已实例化构件多余：走构件取消/报废流程（留史），不删除实例。
  4. "计划版本不是简单覆盖旧值"：任何字段变更 = 新版本行 + plan_adjustment 事件（原值→新值、原因七分类）。
- **真实数据验证**：清单数据不涉及计划；规则动决（与 P-15 版本化一致并细化）。

### RED-13 构件清单导入成为正式业务过程

- **原问题**：真实 Excel 已证明存在标题区、双语表头、空白行、合计行、多 sheet、公式、序号断号等现实结构——"固定第 X 行表头 + 直接插库"不可行。
- **最终规则**：新增正式导入过程域实体（领域模型 3.3 域已补）：
  - `component_list_import_batch`：原始文件名、**file_hash（SHA-256）**、导入人、导入时间、sheet 检测结果、表头识别结果、字段映射版本、批次状态、成功行数、失败行数；
  - `component_list_import_error`：失败行号、原始行内容快照、错误类型、错误信息、处理状态；
  - `import_field_mapping`（版本化配置）：表头名/列位置 → 领域字段的映射。
  - 流程（必须全部落库留痕）：`source file → import batch → sheet detection → header recognition → field mapping → validation → preview → approval/confirmation → formal import → result`。
  - 校验内容：必填、类型、编号唯一性（子项目+构件号）、重量复验（|总重−单重×数量|>容差 → 警告不拦截）、类型字典映射失败清单。
  - 记录项核对（指令清单）：原始文件 ✓、文件 hash ✓、导入批次 ✓、导入人 ✓、导入时间 ✓、字段映射版本 ✓、成功/失败行数 ✓、错误明细 ✓、可重复导入规则 ✓、幂等规则 ✓（RED-14）。
- **真实数据验证**：两份真实清单的全部结构怪异（标题区/双语/空白行/合计行/公式/断号/18+6 类型值）均已由审查文本逐行核实，导入过程必须以"识别+确认"应对，不能假设规范格式。

### RED-14 导入幂等与失败回滚语义

- **最终规则（架构默认，业务可否决）**：
  1. **幂等身份**：`(subproject_id, file_hash, mapping_version)` 唯一。同文件重复上传：命中已有批次 → 拒绝重复生成 component_list_item / actual_component / BOM / part_instance；提供两个选项：仅比对差异报告，或"作废原批次重新导入"（作废需审批，且原批次生成的构件实例**无任何生产事实**方可作废）。
  2. **失败语义默认 B（部分成功）**：校验阶段全量校验不落库 → 预览 → 确认后，成功行 + 批次头 + 错误明细**同一事务**落库；批次状态 ∈ {success, partial_success, failed}；失败行不阻塞成功行，独立修复重传（新批次）或人工补录。
  3. 配置开关 `strict_all_or_nothing`：若业务要求"第 587 行失败则 600 行全不落库"，切换为 A 模式（全部回滚）；两种模式均由批次状态机表达，**不允许编码阶段临时自决**。
- **OPEN 标记**：`OPEN / NEED BUSINESS DECISION` —— 默认 B（部分成功），需业务确认是否强制 A。不确认的风险：若业务默认期望 A 而实现为 B，会出现"不完整清单进入生产"的误解；批次状态与错误明细两种模式下都完整留痕，返工成本可控（不阻塞第二阶段表结构设计，仅影响导入服务流程配置）。

### RED-15 构件类型正式化

- **真实数据证据**：F2 备注列 18 值中混有"备带抗剪键/备带角钢"（**特征说明**）与"钢柱/钢梁/系杆/隅撑/抗风柱/门框/窗框/屋面檩条/女儿墙柱/雨棚梁/梯梁/气楼/牛腿翼缘/散发件/支撑/抗剪键"（**类型**）；F1 备注列 6 值（套管/拉杆/支座/次构件/直发件/高频焊）同样类型/特征/工艺混列。
- **最终规则**：
  1. `component_type` 成为**正式业务属性**：新增字典表（C 类）：code、名称、类别组（主构件/次构件/散件/其他）、统计标记。

- **验证**：18+6 个真实取值已全量枚举（第 0 节），映射规则可覆盖；待业务提供正式类型字典全集（OPEN：字典初值需业务确认）。

### RED-16 制作班组字段语义

- **真实数据证据**：F1"制作班组"9 值 = 8 个班组 + "外协"（供应/外协标记混列）。
- **最终规则**：Excel"制作班组" = **工程来源的初始主责班组计划值**（导入事实），落位：
  1. 导入行快照保留原值（source/raw data 层）；
  2. 映射为 `primary_team_assignment` 的**初始建议值**（状态 = planned，待生产主管确认生效）；
  3. **不等价**于工序执行班组（execute_team 只来自任务/报工事实）、不等价于实际作业人员（worker 只在报工）；
  4. "外协"类取值字典化时标记 vendor/外协属性，主责班组指派可指向外协班组，但执行统计仍按实际报工。

### RED-17 构件清单字段归属表

- **最终规则**（11 个真实字段逐项归属，杜绝全塞 component_list_item / remark）：

| Excel 字段 | 归属层 | 落位实体/说明 |
|---|---|---|
| 构件编号 | 构件主数据 | component_list_item.component_no（子项目内唯一） |

### RED-18 重量语义彻底收口

- **最终规则**：
  1. 清单"单重" = **单个构件的理论计算重量**（深化设计值，导入事实），不是实测重，也不是材料理论重。
  2. 清单"总重" = 导入文件中的**计算值**（=单重×数量），不是独立来源事实；系统存储：导入原值 + 计算复验值 + 差异标记（F2 实测：215 行精确等、11 行 ±0.015 舍入差）。
  3. 重量继承与覆盖链：`清单理论重 →（继承）构件理论重 →（可被补充）构件实测重（报工度量事实）→（冻结）发运快照重量`。
  4. 统计规则：完成重量默认取实测重，缺失回落理论重（口径可配置，全公司统一，不允许页面间不一致）；理论值重算产生**新版次**，不回改任何历史事实行。
- **真实数据验证**：F1 单重 0.91~351.9kg 全量非空；F2 总重 226 行全量非空且 11 行舍入差已逐行定位（2NT-1、2QL-1、2XG-15、2YC-2/3 等）。

## 二、ORANGE 项整改决议

### ORANGE-01 共享库存与数据权限

- 规则：`material/material_batch/stock` 的**所有权（公司）**与**项目归属（分配/使用）**分离：
  - 所有权：owner = 公司（集中采购 N-4 下采购单可无项目归属）；
  - 归属：`po_item_allocation` 分摊 + 领用/消耗动作才把数量落到具体 subproject（stock_ledger 行带项目维度）；
  - 使用权/消耗：过账事实行决定；余料入池后归属回到公共池（可配置按主项目池/公司池）。
- RBAC：公司级角色可跨主项目查询共享库存；子项目级角色仅可见"已分配/已领用到本子项目"的行；共享池行对子项目只读（领用动作走申请/过账，不开放直接改）。

### ORANGE-02 多角色权限

- 规则：功能权限 = **角色并集（union）**；"事实保护类"操作（删除/覆盖原始事实）默认 deny 且不受并集放大（deny precedence 仅此类）。
- 数据范围 = **角色范围并集（union）**（用户可见 = 其所有角色范围的并）；写操作校验按最严路径（服务端行级重校验）。
- 角色与数据范围分开配置、分开计算；禁止实现阶段引入隐式继承或取交集规则。

### ORANGE-03 弱网络/重试/重复扫码

- 规则：所有"提交类"动作必须携带 `client_token`（终端生成 UUID，重试复用同一 token）+ 服务端唯一约束 + 业务防重键（第 14 章双层机制不变）。
- 重复发送同一动作 → 服务端识别已受理 → 返回首次结果，不重复落库。
- 离线：V1 不实现离线队列；未来若支持，离线事件必须携带 occurred_at + client_token + 设备标识，落地时统一去重——**规则先立，实现可后**。

### ORANGE-04 occurred_at / recorded_at 与补录窗口

- 规则：occurred_at 可填报（合理范围校验：不得晚于服务器时间、不得早于开工事实），recorded_at 恒为服务器时间不可改。
- 补录窗口（默认值，可配置）：≤72 小时：自由补录；>72 小时：必填原因 + 班组长审批；>30 天：管理员 + 原因 + 走更正流程留痕。
- 目的：防止人工改发生时间操纵 OEE/节拍/延迟率/绩效/设备利用率；所有超窗补录留审批痕迹。

### ORANGE-05 设备停机与生产影响

- 规则：equipment_event（停机事实）与任务时间重叠**不自动推导**"受影响"；影响关系由 `equipment_impact` 显式登记（系统按"时间重叠 ∩ 任务设备引用"给建议清单，人工确认）；
- 影响记录：关联工序/任务、影响说明、原因可选；不自动改任务状态，不自动改报工事实。

### ORANGE-06 异常中心：根因与影响对象

- 规则：`exception_event`（根因，一条）+ `exception_impact`（影响对象多行：对象类型 + 对象 ID + 影响说明）。
- 一个根因（如设备故障）影响多个构件/任务/工序 → 一条异常 + 多条影响行；**禁止**为每个受影响对象复制独立异常；闭环状态只在根因异常上管理，影响行随根因关闭联动（可单独标注处置结果）。

### ORANGE-07 发运、退运、重发

- 规则：区分四个事实：shipment（发运事件）、shipment_line/snapshot（行/快照）、构件交付状态（delivery status）、return/reshipment（退运/重发事件）。
- 构件交付状态机：`not_shipped → shipped → site_received`，旁路 `returned`（退运）→ 重发以**新 shipment** 承载（新快照行），构件状态回到 shipped。
- 统计双口径（强制并列输出）：
  - **事件次数口径**：COUNT(shipment/return 事件)（发运 1 + 退运 1 + 重发 1 = 3 次事件）；
  - **独立构件口径**：COUNT(DISTINCT 构件 where 最终交付状态=site_received)（= 1 个构件）。
  - 禁止把"发了 3 次"报成"发了 3 个构件"。

### ORANGE-08 现场收货 ≠ 安装 ≠ 项目完工

- 规则：MES 边界到 `site_received`（现场收货）为止。
  - site_received **不推导**"已安装"；V1 不建安装实体、不建安装状态（现场扫码域预留扩展位：若未来增加"安装确认"事件，作为新增事件类型扩展，不改既有状态机）；
  - MES 语境的"项目完工" = 发运完成（shipping→completed 状态机），与土建/安装完工无关；
  - 文档与报表用词必须区分"交付（delivered/site_received）"与"安装（MES 外）"。

### ORANGE-09 图纸换版/工程变更处置

- 规则：drawing_revision 只追加，新版不覆盖旧版；变更登记时对受影响构件**当时状态快照**（未开始/进行中/已完成未发运/已发运）：
  - 未开始：换新版重排（旧计划行留史）；
  - 进行中：技术核定单决定（按旧版继续 / 返工 / 报废重制），核定与执行全留痕；
  - 已完成未发运：核定是否返工/放行（放行走审批，留痕）；
  - 已发运：记录变更与影响，不回改发运快照；必要时走售后/补件流程（新构件 lineage）。
- 铁律：新图纸版本**永不覆盖**旧版本下已产生的历史事实。

### ORANGE-10 库存盘点/纠差

- 规则：盘点差异处理 = **新事实**，不修改原库存事实行：
  - inventory_check 明细登记账实差异 → 差异经审批后生成 stock_ledger 的盘盈/盘亏调整行（新事实，引用盘点单）；
  - 差异性质在盘点单上分类：normal（正常损耗容差内）/ correction（登记错误的更正，联动更正流程）/ adjustment（授权调整）；reversal 仅用于原事实行冲正（更正域）；
  - 超阈值差异 → 异常中心（仓库异常）+ 强制原因；禁止"直接改 stock_balance"——余额永远可由流水重建。

# R5 节 设计裁决：responsibility_type 与 responsibility_kind 冲突（2026-09-20 第 5 轮）

> **触发**：第 5 轮独立验收发现《班组能力-构件类型-工艺模板-劳务计价业务设计审查报告》使用 `responsibility_type`，而当前 V1.2 实际实现使用 `responsibility_kind`；该报告还设计了 `labor_settlement_record`/`labor_settlement_line` + `rule_version_id`/`unit_price`/`matched_condition_ids` 快照，而当前 V1.2 数据库并未完整采用该 settlement line 模型。
> **本轮权限**：仅做文档同步与命名裁决，**禁止改代码/DB/View/Service/Migration/Test**。
> 业务规则落点见 `v1.2_business_decisions_v2.md` 第二十一部；数据模型落点见 `v1.2_database_domain_model.md` 第 23 章。

## 一、两个设计的差异

| 维度 | 设计 A（《班组能力…审查报告》研究稿） | 设计 B（当前 V1.2 已落地实现） |
|---|---|---|
| 责任字段名 | `responsibility_type` | **`responsibility_kind`** |
| 责任取值 | 未在该稿中正式冻结（其劳务结算示例用 `responsibility_type` 作标记） | `TEAM` / `NON_TEAM` / `PENDING` / `NULL`（迁移 `c6a7b8c9d0e1` 引入，已验证） |
| 计价来源 | 未来 `labor_settlement_record` 按 `responsibility_type` 区分是否跳过/标记 | `effective_chargeability`（视图 `c7b8c9d0e1f2`）由 `responsibility_kind`+责任/执行班组推导 |
| 结算记录 | `labor_settlement_record`（◆ 未来可选）含 `rule_version_id`/`unit_price`/`matched_condition_ids` 快照 | 当前**无结算记录实体**；仅责任判定 + 计价资格推导 |
| 状态 | 设计研究稿，标注 ◆ 未来可选，**未实施** | 已通过 17 真实场景、三条计价链一致、并发 10/10 验收 |

## 二、当前代码实现对应哪个模型

**当前 V1.2 实现 = 设计 B（`responsibility_kind` 模型）。** 证据：
- DB：`prod.rework_order.responsibility_kind`（varchar(16)）+ 3 个防旁路 CK（`c6a7b8c9d0e1`）。
- ORM：`backend/app/db/models/prod_quality.py` 中 `ReworkOrder.responsibility_kind` 与 CK 一致。
- View：`eng.v_operation_cost_trial` / `v_project_production_cost` 的 `effective_chargeability` 完全由 `responsibility_kind` 推导（`c7b8c9d0e1f2`）。
- Service：`labor_settlement_service.classify_chargeability(responsibility_kind, ...)` 同源同逻辑。
- 设计 A 的 `labor_settlement_record`/`labor_settlement_line`/`rule_version_id`/`unit_price`/`matched_condition_ids` 在 V1.2 数据库中**均不存在**。

## 三、设计裁决（Ruling）

1. **`responsibility_kind` 为正式字段名**，`responsibility_type` 是审查/设计研究阶段的**旧称（历史名称）**，**不再作为正式模型字段**。
2. 任何未来结算记录（若经单独设计确认后实施）如需责任分类，必须**复用 `rework_order.responsibility_kind`**（或引用之），**不得另立并行 `responsibility_type`**。
3. 设计 A 中的 `labor_settlement_record` / `labor_settlement_line` + `rule_version_id` / `unit_price` 快照 / `matched_condition_ids` 属**劳务结算系统未来可选扩展**（原稿自标 ◆ 未来可选），**不在 V1.2 责任模型冻结范围内**，且**本轮禁止新增**（第 5 轮 §八）。
4. 不为了迁就旧文档而回改代码：文档向已验证实现对齐，而非实现向旧设计稿对齐。
